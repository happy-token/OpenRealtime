# 语音播放、弱网缓存与轮次竞态需求

日期：2026-10-02。状态：播放上下文与首音前续说已落地；缓存、WebRTC 和暂停恢复仍为后续需求。

本文补充 JEV-TURN-TAKING-PRD.md 与 TURN-COORDINATION.md。播放事实、缓冲和传输接口是确认的设计方向；复杂交互的默认行为为待对齐建议。本文下方区分已落地行为与后续需求。

## 目标与职责

- 语义打断的主要上下文来自客户端已播放内容；生成、发送、播放分别记录。
- 模型输出语义证据，轮次协调器决定动作，音频输出适配器执行暂停、恢复、取消并确认。
- WebSocket 与 WebRTC 共用轮次和播放事实契约，传输适配器声明进度精度、可暂停恢复和清空能力。
- 弱网下允许客户端自适应预缓存，同时使用队列上限、背压和过期音频拒收。
- 不声称能够证明用户实际听见；只记录设备播放事实或带精度的估算。

## 播放上下文

打断请求需包含：speech_id、response_id、output_epoch、用户开口时的播放位置与文本快照、判断时最新播放位置与文本、精度、进度年龄和缺失状态。

用户开口快照是主要依据；最终历史截断使用实际停止时的播放位置，二者不得混用。优先在客户端输入音频/VAD边界捕获并关联 input_id；服务端 VAD 情况需通过输入音频时间和播放进度关联，不使用 ASR 到达时间冒充开口时间。客户端与服务端时钟不可直接比较。

用 TTS 对齐信息或真实片段音频时长建立文本—音频映射。缺少词级对齐时只确认完整片段，并记录未确认的片段尾部；不把字符比例估算标为精确。进度过期时保留未知信息，不回退到把生成全文视为已播放。

## 缓存与传输

- 客户端持有可控、有上限的预播放队列；网络抖动或断音增加目标缓冲，稳定后逐步减少。首音启动缓冲与后续目标库存分别配置。
- 服务端保存待合成文本、有限未发送音频和时间映射。客户端反馈 buffered_duration；达到高水位后停止提前发送/提交新 TTS 片段，降到低水位恢复。
- 最大库存同时按时长与字节限制；不无限累积 PCM。暂停期间也执行上限与背压。
- WebSocket 分块可提前发送音频给客户端播放器；控制消息不得积压在大量应用音频之后。记录缓冲不足、首音延迟、取消延迟与控制消息年龄。
- WebRTC 音频轨道按媒体时间发送，使用原生抖动缓冲。大规模提前下载是额外的应用缓存能力，不等同于原生 RTP 抖动缓冲。
- WebRTC 的控制消息与媒体无跨通道全序保证；采用播放代次、媒体位置映射和取消确认。不得假设原生接收缓冲可任意清空或精确续播。
- 取消先停止本地旧输出，再异步通知服务端；旧代次迟到音频必须拒收。新代次输出须确认不会重新放出旧尾音。
- 客户端协议：playback_progress、pause、resume、cancel、cancel_ack；进度含播放位置、缓冲时长、phase、精度和单调序号。
- 长时间带宽不足或断网不能靠有限预缓存解决；进入明确的重连/恢复流程，不在新输入后重放旧回复。

## 回复生命周期

至少区分：生成准备中、TTS准备中、音频已排队但未播放、正在播放、暂时暂停、取消中、已结束。首音以客户端输出确认界定，不以模型文本/TTS任务开始/服务器发送首帧界定。

保留 input_id、input_revision、response_id、speech_id、output_epoch 和 cancellation_id。取消绑定特定 response_id；旧取消、完成、进度和语义判断不得影响替代回复。生成完成和播放完成分别记录。

## Case A：已判停，但首音前用户继续说话

建议默认：立即冻结旧回复的输出准入，保留用户新音频；按“首音前续说或修订”处理，不强制使用播放期打断模型。

1. 判停完成但 ASR 尚在最终提交：缓存或路由新音频到后继候选，不因 commit_pending 丢弃 VAD/ASR。明确最终提交前后输入边界。
2. 已提交且 LLM/TTS准备中，用户续说：使旧 response 失去输出资格并发出取消，旧首音即使晚到也拒播。
3. 新输入与上一请求的关系分为追加、修订、替换、独立新请求、纯停止；先实现明确规则和可替换关系判定，不仅依赖固定时间窗。
4. 追加/修订需组成更新的有效请求，避免把未播出的旧回复作为用户已知事实；Journal保留原始输入和 superseded/修订关系，不静默覆盖已提交事实。
5. 普通生成可以取消；已经执行的工具副作用不得通过取消自动回滚或重复执行，必须保留执行事实和幂等标识。
6. 若客户端确认首音已播出，转入播放期插话路径，不以服务器判断覆盖播放事实。

## Case B：连续多次打断

建议默认：同一次连续表达中的多段插话共享候选 input_id，累计 revision；ASR final/提交后才形成新的输入身份。身份划分还需输入边界，不把相邻说话全部合并。

- 第一次插话针对回复 A；取消 A 后，后续“不是上海，是杭州”可以继续修订同一候选，不能因为 A 已停就丢失抢话来源。
- 停止旧回复与用户轮次归属独立：助手已让出后，后续内容走普通判停调度，但保留 interrupt_of=A 和追加/修订关系。
- “停”后来变为“停，查杭州”必须按最新 revision 更新为新任务；早先 stop 不得提前销毁仍可能增长的输入。
- 已提交输入并产生回复 B 后再插话，建立新候选并明确绑定 B；针对 A 的迟到模型结果或取消确认不得取消 B。
- 每个目标回复取消动作幂等；每个有效用户轮次只提交一次。新 revision 撤销旧提交计时器和旧语义证据。
- 不确定/模型错误保留用户请求，但不得无条件把背景声变成抢话；缺乏声源依据需显式记录未知并测试误打断率。

## Case C：助手播报期间用户侧不做语义判停

2026-10-02用户确认：助手响应期间创建的插话候选不调用语义EOT模型，不等待complete/incomplete/uncertain。候选在旧回复让出后仍保留插话归属，直到ASR最终提交结束；下一段独立输入才重新按当时的回复状态分流。

- 打断标签负责是否让出；提交只等待VAD/ASR停止条件、取消确认和ASR final，不等待语义完整性。
- 普通用户轮次继续使用语义EOT；纯停止、附和不生成新回复。
- 这会降低插话响应等待，但语句中的长停顿更可能被视为结束，是用户选择的交互取舍。不得通过隐藏模型等待重新引入EOT。
- 暂停恢复与客户端播放事实仍为后续需求，本次代码修复不表示已实现。

## 当前实现与缺口

现有协调器已支持独立判停/打断插件、输入 identity/revision/token 校验、目标回复取消、让出确认、ASR最终提交、超时恢复。引擎也支持生成完成后取消仍未播放完的音频。

当前 assistant_text 来自累计 BrainTextDelta，不是已播放文本；暂停恢复尚未形成完整能力。回复生成开始与首音播放缺少上述独立场景策略。2026-10-02 已修复 commit_pending 期间后继 VAD/partial 的遗漏、旧轮次 final/让出确认的误归属，以及替代回复的打断目标更新；插话候选不再调用语义判停。首音前续说和客户端播放进度已按下方实现记录落地；完整关系模型、词级对齐、暂停恢复及 WebRTC 适配仍属于后续需求。

## 验收场景

1. complete → LLM开始 → 无首音 → 用户“还有……”：旧音频不得播出，新输入不丢失。
2. TTS已生成/已发送但客户端未播：按首音前场景处理。
3. ASR最终提交等待中用户续说：内容有明确归属，不吞音、不重复提交。
4. 播放 A → “停” → 同次表达“查杭州”：保留完整请求且只生成一次。
5. 播放 A → “查上海” → A取消中“不是，杭州”：修订同一候选，不触发重复回复。
6. B已开始 → 第二次插话：只取消B；A的迟到结果不影响B。
7. “嗯，你继续”与提问后“嗯”：前者可继续，后者可作为回答。
8. 播放期“不是北京，是……杭州”：旧输出快速停止，新回复等待完整表达。
9. 弱网下大量预缓存、取消消息延迟/重排：本地可停止，旧音频不复活。
10. 进度迟到、缺失或词级对齐不可用：不把未播全文作为已播放历史。
11. 工具已执行且首音前续说：副作用事实保留，工具不重复执行。
12. 暂停后继续到达音频：缓存有界；恢复不跳字、不重复播放。

记录：用户开口到本地暂停/取消延迟、最后一音到新首音延迟、错误截断范围、误打断/误恢复、丢输入/重复提交、库存时长、控制消息延迟、旧代次音频拒收。性能数值须通过弱网和真实音频测试后确定。

## 2026-10-02：首音前续说与实际播放上下文实现

- Response 在请求准入时以 preparing 登记，不能等 BrainResponseStarted 才识别待取消回复。已提交轮次尚未登记回复时，后继输入保持续说身份并等待 preparing，不调用 EOT。
- 用户开口时尚无播放开始确认：取消旧回复，将上一最终转写与本次最终转写组合成有效请求。新 Journal Item 的 `continuation_of_turn_id` 保留修订关系；模型投影排除被替代 user/assistant，保留工具执行结果。若 ASR 仍使用旧 turn_id，提交时生成新身份，避免稳定 Item ID 碰撞。
- 明确的“停”仍只停止；“换个问题／另一个问题／新的问题／重新开始”按独立请求处理。追加和修订通过组合上下文表达，完整可替换关系分类器尚未实现。
- 一旦客户端确认播放开始，后继输入走播放期插话，不再合并原用户输入。每个候选固定用户开口时的已播放文本快照；之后播放的新内容不改写该快照。
- BrainTextDelta 和 Journal 助手全文不再写入 spoken-text 观察。只有 `ReportPlaybackProgress` 的交付前缀更新打断上下文，旧 response 的迟到报告不能覆盖当前回复。
- Doubao 的 TTSSentenceEnd 保留原句，通过独立 `TtsTextAlignment` / `SpeechTextAlignment` 建立原文句尾与累计 PCM 时长的映射。只确认播放位置已越过的完整句段；文本归一化导致无法匹配时保留未知尾部，不猜字符比例。未提供对齐信息的供应商在完整播放前保留空的已确认文本，完整播放后确认全文。
- 浏览器每 100ms 回报 `playing` 采样位置，按真正调度的音频片段累计，排除弱网造成的空白间隔。精度为 SEGMENT，不能声称精确到词。WebRTC 可使用相同的播放进度／文本对齐事件，当前没有新增 WebRTC 传输实现。

供应商事件字段核对：[火山引擎 TTS 流式协议](https://docs.volcengine.com/docs/DoubaoVoice/WebSocketUnidirectionalStreaming-V3?lang=zh)。本次验证为本地自动化回归，尚未进行真实麦克风与供应商会话测试。

## 2026-10-02：播放与显示同步

- 参考本地 VoiceLoop 的客户端播放时钟与 TTS 对齐实现。服务端发送 `assistant_text_alignment`，携带 speech_id、generation、累计文本前缀及音频起止位置；生成文字先缓存，字幕和对话文字跟随浏览器实际播放位置更新。
- Doubao 请求开启 `enable_timestamp`，保留供应商的词级起止时间。重复时间戳去重，存在有效词级信息时不再叠加句子全文，避免重复显示。无词级信息时使用句段音频边界；完全没有对齐信息时以真实累计音频时长提供整段显示，不按字数估算词速。
- 客户端允许迟到对齐信息追上当前播放位置；generation 与 speech_id 隔离旧消息。打断后冻结到已完整播出的对齐前缀，迟到字幕和结束事件不能补回未播放文字。首音前 TTS 失败仍显示文字回复，并标为失败。
- 第三方数字人播放器当前仅有播放起止事件，保留整段显示，尚不具备逐词同步。当前验证覆盖本地自动化回归，真实供应商会话、麦克风及弱网实测仍待验证。
