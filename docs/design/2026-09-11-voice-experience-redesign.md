# OpenRealtime 语音体验设计评估与新方案

> 当前执行清单与最新状态见 [Session 对话体验任务规划](2026-09-11-session-experience-task-plan.md)。本文件保留调研与方案演变，不代表所有提案已实施。

日期：2026-09-11。阶段：调研与方案，不是已实施的产品改版。

## 1. 判断与范围

现有产品已经有沉浸式声场、数字人、可收起配置台、三种通话布局和流式对话基础。下一步最有价值的投入是完善连续对话的可理解性、可控性和恢复能力，再统一视觉表达。

建议方向：**安静、有回应的对话空间**。保留声场与数字人的识别度，让当前一句话、当前状态和下一步操作成为交互主线。

本次以首次体验者和经常使用语音的用户为主要对象，兼顾企业演示。开发者配置与数字人资产管理是独立的次级工作流。如果最终重点是呼叫中心坐席或内部运营，需要另行补充业务任务与权限研究。

证据：读取当前工作区实现，浏览官方设计资料，检查 1440×1000 桌面与 390×844 移动端页面；通话布局使用仓库既有模拟 WebSocket / SpeechRecognition 夹具检查。未测真实 ASR/TTS 延迟、噪声下打断、数字人口型同步或真实手机浏览器。模拟流程不代表真实语音质量。

## 3. 当前设计评估

### 值得保留

- 配置台默认 collapsed，已经实现渐进展开，不应误判为首屏堆满配置。
- voice/avatar 与 fullscreen/sidecar/content 的分离，以及保持同一体验表面的结构，利于稳定布局切换。
- 文字发送失败保留草稿；转录有 interrupted/failed 标记和回到最新消息。
- 具备语义标签、焦点样式、安全区和响应式规则，是继续优化的基础。
- 深色背景与声场具备品牌辨识度，无需另造一套泛化后台皮肤。

### 按影响排列的问题

| 优先级 | 证据与观察 | 用户影响 | 建议 |
| --- | --- | --- | --- |
| P0 | `open-realtime-app.tsx` 的恢复麦克风失败设置 micError；`call-view.tsx` 只在首页分支把 error 交给 HomePreviewWorkspace | 通话内恢复失败可能看不到原因 | 会话级错误区域覆盖所有布局，提供重试、设备设置与文字入口 |
| P0 | `beginSession()` 必须先成功 `engine.start()` 才显示会话；首页 connected 又依赖 micAvailable | 麦克风不可用用户难以抵达已有文字输入 | 分离“进入会话”与“开启麦克风”；文字入口不依赖麦克风权限 |
| P1 | `engine.stop()` 停麦克风，未停止当前播放；主视觉却显示“已暂停” | 用户可能以为 AI 也已暂停 | 改成“麦克风已关闭”；另设停止回复，明示作用范围 |
| P1 | `SessionControlBar` 中 showComposer 在非全屏恒为 true，但键盘按钮仍切换 composerOpen | 点击“收起”却不收起，标签与效果不一致 | 非全屏改为“定位输入框”或允许真实折叠，并统一可见状态 |
| P1 | 首屏 h1 是主题名“云雾”，文案强调 LIVE PREVIEW；移动端截图可见 | 主题价值比对话用途更突出；首次开口缺乏方向 | 主标题介绍对话用途，主题名降为配置摘要；加三个可编辑开场建议 |
| P1 | `startPresentationSession()` 固定 fullscreen；完整记录在全屏隐藏 | 工作型对话需要额外查找记录；首次使用不易发现布局 | 增加可见的“对话记录”入口，记住偏好；桌面首次默认并排作为待验证假设 |
| P1 | `terminateSession()` 直接返回首页 | 结束后的回顾、复制与下一步缺少入口 | 结束后立即释放音频，再显示轻量结束页；先保留原始记录，再异步生成可选总结 |
| P1 | 控制区六个图标依赖 tooltip；菜单术语含 Sidecar、内容 | 手机无悬浮提示，功能难识别 | 核心操作配短标签；布局名改“专注 / 并排 / 阅读” |
| P1 | 全屏字幕 CSS 为 clamp(.76rem,1.05vw,.88rem)，基准16px时约12–14px | 核心信息小于其重要性；远距离阅读困难 | 桌面20–24px、手机18–20px作为原型起点；两三行稳定字幕区 |
| P2 | <=680px 操作按钮40px，较前一断点44px更小 | 高频触控容错下降 | 采用48px触控目标；减少一级按钮数量，避免挤压 |
| P2 | reducedMotion 未直接传入 Orb，CSS虽有系统减少动态规则 | 应用设置与JS/WebGL动画是否同步尚未确认 | 逐类主题检查，统一系统偏好与应用设置，提供静态声场 |

代码结论与视觉判断应分开理解：以上控制逻辑可由代码直接核实；字号和布局的最佳值需要后续可用性测试，不给出伪精确的设计评分。

## 4. 新信息架构与视觉方向

一级工作空间：对话。辅助入口：最近会话、角色与声音、设置。资产编辑、模型、工具、驱动方式进入工作台，不占会话核心位置。

视觉使用现有深色体系：石墨底、低饱和表面、一个品牌强调色；危险红仅用于结束与严重错误。监听、处理中、回复中通过文案与形态共同区分，不能只靠颜色。正文区域避免大面积透明叠底；玻璃质感集中于控制区或少量浮层。

排版建议：正文16–18px；沉浸字幕20–24px；标签12–14px仅用于次要信息；标题28–36px。间距以8px节奏组织，面板16–20px圆角，按钮10–14px圆角。实际值应映射现有 tokens，而非持续追加互相覆盖的 CSS。

声场默认克制，发声时才有明确响应。用户输入电平与AI播放状态分别驱动反馈；未接入麦克风的预览不得暗示“正在听你说”。入场只做一次，常驻内容不漂浮、不持续争夺视线。

## 5. 关键页面方案

### A. 开始前：降低第一次开口成本

主文案：“想聊什么？直接说就好。”下方说明：“可以随时打断，也可以打字。”仅在真实支持时显示。

中间保留适中声场或数字人肖像；下方一个明确主按钮“开始对话”，一个次级入口“先打字”。角色、音色、设备以一行摘要呈现。提供三个能力范围内的开场建议，例如“帮我理清一个想法”“陪我练一段表达”“解释一个概念”；点击后允许查看和修改，再开始。

首次点击时才申请麦克风；如已有权限快速进入。按钮分辨“等待麦克风授权”“正在连接”“准备就绪”，不把所有问题归为“正在连接”。设备测试是可选路径，不能成为每次进入的强制流程。录音和转录保存提示必须依据真实数据策略。

### B. 通话中：一套控制、三个视图

- 专注：中央声场/数字人 + 两三行当前字幕 + 可见的记录入口，适合轻量聊天。
- 并排：左侧约60%对话记录，右侧约40%声场/数字人；拖动比例只作为高级功能。适合讨论、演示、工作。
- 阅读：内容居前，小窗陪伴；不能遮住最新消息、结果操作或输入框。

桌面首次默认并排是本方案的产品假设；移动端先用专注。记住用户主动选择，禁止因AI输出变长而突然改变布局；可显示“展开详细内容”建议。

核心控制稳定为“麦克风 / 打字 / 结束”，其余放入更多；AI回复中增加“停止回复”而不替换麦克风位置。结束按钮与其他操作留出距离。常用按钮有可见短标签，语义与实际作用严格一致。

文字记录保留滚动意图；流式文本不反复整段重排。临时识别文本与已确认文本用字重或底色区分；已打断内容保留标记。并排视图关闭临时字幕时也需解释该开关只影响浮动字幕。

### C. 结束后：让对话有结果

先停止采集和播放，立即展示“本次对话已结束”。保留本次记录，提供复制、返回首页；在具有真实存储能力后提供保存与继续。自动摘要应明确标记 AI 生成，生成失败不影响记录访问。

“重新开始”与“继续这段对话”需区分。未实现上下文恢复之前，不展示会暗示恢复的按钮。

### D. 数字人专属细节

复用相同状态、字幕、控制区，避免建立另一套操作语言。人物眼线和字幕有固定安全区域，不裁脸、不遮嘴；加载时使用该人物静态封面与真实准备阶段，失败时提供同角色语音降级（须能力支持）。

打断后立即停止音频并同步取消旧口型/动作；保留人物身份和上下文。素材循环不在说话过程中突然跳回待机；加载失败、准备超时、口型落后分别定义反馈。此部分本次未做真实运行验证。

## 6. 交互状态规范

连接、麦克风、回复/工具执行是三个独立维度，应组合表达；不能只把所有状态塞进一个 loading 枚举。

| 场景 | 可见反馈 | 用户能做什么 |
| --- | --- | --- |
| 等待授权 | “请允许使用麦克风” | 查看帮助、改用文字、取消 |
| 正在连接 | “正在建立语音连接…” | 取消；超时后重试 |
| 等待用户开口 | “我在听，你可以开始说了” | 说话、打字、静音 |
| 检测到用户说话 | 即时电平反馈 + 临时转录 | 继续说，不因短停顿立即抢话 |
| 用户结束一句 | 保留最后识别内容，稳定过渡 | 补充或打断即将开始的回复 |
| 回复准备中 | “正在组织回复…” | 修改需求、停止回复 |
| 工具运行中 | “正在查找资料…”等真实动作描述 | 查看进度；仅在可取消时显示取消 |
| AI讲话 | “正在回答 · 可随时打断” + 同步字幕 | 开口打断或点击停止回复 |
| 用户打断 | 停止旧音频与动画，记录标记“已打断” | 立即说新内容 |
| 麦克风关闭 | “麦克风已关闭”，AI仍讲话时同时显示播放状态 | 开麦、打字、停止回复 |
| 网络中断 | “连接中断，正在尝试恢复” | 查看现有记录、保留草稿、重试/结束 |
| 恢复成功 | 只在确认续接后说“已恢复，可继续” | 继续；不自动重播旧尾音或重复执行工具 |
| 恢复失败 | 明确失败原因与可用下一步 | 重试、新建会话、复制当前记录 |
| 长时间等待 | 更新等待提示，不伪造进度百分比 | 停止或重试；避免无限循环 |
| 结束 | 记录与可选摘要 | 复制、返回、在支持时继续 |

语音打断仅取消播放并不等于取消已经发生的外部操作。确认卡需展示动作、目标、关键参数和执行结果；取消的语义必须匹配后端能力。

## 7. 动效与反馈预算（提案目标，非当前测量值）

- 点击后的视觉确认：100ms内。
- 普通控件反馈：120–180ms；布局切换：220–320ms；减少动态时使用直接切换。
- 已检测到语音后界面反馈：100ms内；检测本身的耗时单独记录。
- 客户端收到取消事件到本地停止播放：P95目标150ms内；端到端打断另测。
- 等待超过约1秒显示处理状态，约4秒提供具体解释，约10秒提供明显恢复入口；这些是原型起点，应按实际服务分布调整。
- 首音延迟单独统计：用户真实停止说话 → 端点判定 → ASR完成 → 首文本 → 首音频可播放 → 实际播放。禁止用转圈更快来冒充响应更快。
- 字幕按可读短句推进；若没有音频时间戳，先按句显示，不假装实现逐字同步。

## 8. 验收与落地

### 第一阶段：行为与恢复

覆盖通话中错误提示、无需麦克风的文字入口、静音语义、键盘按钮效果、结束后记录。按现有职责修改 OpenRealtimeApp、CallView、SessionControlBar、presentation-model，后端能力不足的恢复/总结另列任务。

### 第二阶段：主体验改版

重做开始前信息层级、状态区域、稳定字幕、核心控制、布局命名；完善移动端。先交付可点击原型，覆盖正常流程及拒绝授权、打断、断线、结束。沿用现有会话表面，避免切换布局重建媒体连接。

### 第三阶段：精修和实测

统一设计变量、检查各主题减少动态、优化数字人衔接；用真实麦克风、弱网、长回复和中英混输验证。通过功能开关分批启用，保留对照，避免一次性重构所有页面。

### 最小验收场景

1. 首次用户能指出如何开始、如何停止、如何打字；建议先招募5–8名目标用户做形成性测试，不把小样本当统计结论。
2. 拒绝麦克风后可完成文字往返，不丢失草稿。
3. 说话中静音、AI回复时静音的结果符合文案；停止回复有独立动作。
4. 一轮回复中切换三个视图，音频、上下文、字幕不重启。
5. 用户回看旧消息时不被滚动抢回；返回最新入口可见。
6. 断线后保留当前记录，恢复不重复播报或重复发送。
7. 结束立即关闭音频，原始记录可访问，摘要失败可恢复。
8. 390×844、320px窄屏、横屏、200%缩放、软键盘和安全区下关键操作可达。
9. 键盘焦点、屏幕阅读器完成态播报、减少动态、颜色辨识分别检查；避免逐字字幕重复播报。

衡量首次成功开口时间、首轮完成率、授权失败后的恢复率、打断到停声延迟、断线续接率、结束后结果利用率。先采集当前基线，再设提升目标。当前未测这些数值。

## 9. 页面结构草图

桌面并排模式：

```text
┌───────────────────────────────────────────────────────────┐
│ OpenRealtime    当前角色              专注 / 并排 / 阅读  │
├────────────────────────────────┬──────────────────────────┤
│ 对话记录                       │                          │
│ 你：帮我理清这个想法……          │      声场 / 数字人       │
│                                │                          │
│ AI：我们可以从三个问题开始……    │     正在回答             │
│                                │     你可以随时打断       │
│ [回到最新]                     │                          │
├────────────────────────────────┴──────────────────────────┤
│ 输入补充内容……                              [发送]       │
│ [麦克风 开]  [停止回复]  [更多]                [结束]       │
└───────────────────────────────────────────────────────────┘
```

移动端专注模式：角色与记录入口在顶部，声场居中，固定两三行字幕紧邻控制区；底部麦克风、打字、结束保持位置。软键盘出现时收小声场，优先保留输入框与最近消息。布局重排不改变当前会话。

## 11. 用户反馈后的方案收敛（2026-09-11）

已确定的要求：说话状态使用 Siri wave 内部彩色光束，不保留圆形外壳；横向拉长并放到底部，根据语音音量改变高度，无声时收成细线。参考 [Liquid Orb Editor](https://lersent001.github.io/orb/) 中 orb-glass-liquid / siri；采用用户链接中的黄 #FFD86B、青 #82F4FF、粉 #FF7BD5、紫 #8E6CFF。预览为该方向的独立概念重绘，不是原始着色器的逐像素复刻。

已确定的体验范围：结束立即停止音频，保留本次记录，提供回顾、复制和可选总结；所有布局统一提供错误反馈、重试与文字入口。

需核对的文案：开始前“想聊什么？直接说就好。”，副文案“可以随时打断，也可以打字。”；倾听“我在听”；准备回复“正在组织回复…”；说话“正在回答”；静音“麦克风已关闭”；断线“连接中断，正在尝试恢复…”；结束“本次对话已结束”。这些尚未获得用户最终确认。

待核对的音量语义：建议用户说话时跟随麦克风音量，AI说话时跟随实际播放音量，无声音时回落为细线。麦克风关闭但AI仍在播报时，光束继续响应播放音量。无声思考仅保留细线色彩缓慢流动，不模拟不存在的声音幅度。

已制作独立可切换状态的设计预览，包含音量滑杆、三种布局、错误恢复、结束回顾及 A 丝带光束 / B 克制细光两种可调方向。未更改正式产品页面；预览不访问麦克风、不播放音频、不连接真实会话服务。

位置进一步确认：光束贴窗口最底部边缘横向展开，发声时向上起伏，无声时回落为底边细线。控制按钮与文字输入保持在光束上方；所有布局沿用相同底边锚点。独立设计预览已更新。

最终视觉方向确认：用户选择 **方案 B「柔和极光」**，后续底边声音状态采用这一方向。贴窗口底边、发声时向上柔和扩散、音量决定高度、无声时回落细线。已单独保存选定原型；原丝带光束作为历史设计保留。此确认不等于引导语或其他待核对项已获批准。
