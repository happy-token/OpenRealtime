# OpenRealtime 用户对象研究与文档受众建议

研究日期：2026-10-12。状态：案头调研已完成。用户随后明确：产品首先介绍可自定义、可打断的语音交互 Agent，恢复成本、灵活性、丰富功能与 Chat Agent 接入亮点；产品资料问答作为第一个上手示例，数字人为可选能力。本文为 README、项目文档与前端文档页面的整理提供依据，不表示已完成用户访谈、产品市场匹配验证或新功能验收。

## 建议先聚焦谁

**优先验证的采用者：有自己的资料、角色或业务逻辑，希望借助现有 Web 应用构建可配置语音助手，并按需加入数字人的独立开发者与小型产品团队。**

“全球开发者”可以作为覆盖范围，但不足以指导首屏文案。更有效的识别条件是：正在做一个具体的交互应用；愿意配置云服务与承担应用部署；希望控制回答模型、声音、资料和人物；能够接受当前支持范围，并愿意验证自己的场景。

首个建议展示场景是**用自己的产品资料配置一个能讲解、问答、被打断和纠正的助手**。它可以先用纯语音，随后增加数字人，能把当前的角色、知识、语音与呈现界面串成一条路径。当前资料回答质量仍需按数据集和配置验收，不承诺知识导入后自动获得可靠客服能力。

第二类候选是角色与数字人体验的创作者、自部署爱好者；教学、面试或销售角色扮演的产品团队值得作为后续验证对象。已有编码 Agent 的语音使用者也有明确需求，但本项目统一接入和完整语音任务协作仍为 TODO，不宜用该承诺吸引首批用户。

以上是从外部需求信号和本地交付范围推导的建议，尚不是 OpenRealtime 已有用户的统计结论。

## 研究范围与证据限制

本轮读取了本地中英文 README、产品定位与证据矩阵、启动与云服务指南、角色与知识指南、数字人指南、前端文档目录和 ESP32 参考客户端说明；另核查相近项目的官方说明、公开 issue，以及数字人供应商发布的客户案例。

证据分为四种：

| 类型 | 可以回答什么 | 解释限制 |
| --- | --- | --- |
| 官方产品说明 | 项目面向什么场景、提供什么入口 | 证明供应方定位，不能代替真实采用与留存数据 |
| 用户公开需求与故障反馈 | 具体的人曾遇到什么问题或想完成什么任务 | 搜索样本偏向活跃技术用户与遇到问题的人，不能推算需求占比 |
| 供应商客户案例 | 某组织曾将交互数字人用于特定业务 | 属于供应商选择和发布的案例；不等于独立效果评估或开源采用意愿 |
| 本地实现与文档 | 本项目哪些入口能承接某类需求 | 工作区有未提交修改；不自动等同公开发布版，也不证明完整体验通过 |

通过 GitHub 连接器确认 [OpenRealtime 仓库](https://github.com/happy-token/OpenRealtime)为 public；查询 `repo:happy-token/OpenRealtime is:issue` 本次返回空列表。这只说明本次查询没有可用的直接 issue 样本，不能推导项目没有用户或没有需求。本轮没有项目站点行为数据、部署成功率、访谈、复访或付费数据，因此不估算人群规模、转化率和商业收入。

2025 年 issue 在本文中作为历史需求样本；不据此断言竞品在 2026 年仍有相同缺陷。官网按本次读取时的内容解释，具体版本和承诺仍需在实施选型时复核。

## 把用户的三种角色分开

同一产品通常有三种用户角色，文档要分别承接：

| 角色 | 常见身份 | 最先关心 | 合适入口 |
| --- | --- | --- | --- |
| 体验者 | 想试试语音或数字人的访客；应用最终使用者 | 能帮我做什么，如何开始，如何停止或重试 | 在线体验、场景演示、首页使用指南 |
| 构建者与部署者 | 独立开发者、小团队工程师、技术创作者 | 怎么做成自己的助手；要哪些服务、费用与资源；如何保存数据 | 本地启动、真实服务配置、角色与知识、部署指南 |
| 扩展者与贡献者 | 语音工程师、框架开发者、供应商适配作者 | 如何换模块、追踪故障、验证取消和会话行为 | 架构、插件合约、接口、诊断与贡献指南 |

构建者负责采用，体验者验证应用价值，扩展者推动生态。这一划分是阅读路径设计，不是已测得的流量分布。把三类人放在同一个按文件排列的目录中，容易让体验者先看到内部规划，让构建者找不到第一条可复现路径。

## 候选受众逐项分析

### 1. 知识与业务助手的构建者：建议作为第一优先级

**想完成的任务：**把自己的产品文档、业务说明或知识服务做成能直接交流的助手；先得到可试用的 Web 应用，再调整角色、声音与呈现。

外部依据包括 Pipecat 的应用型 RAG 请求与语音来源处理需求。内部依据包括[角色配置](../guides/ROLE-CONFIGURATION.md)、[知识管理](../KNOWLEDGE-BASE-GUIDE.md)、[历史与记忆](../MEMORY-AND-HISTORY-GUIDE.md)及现有 Web 工作区。

**采用触发：**已有文字助手或资料，希望增加语音；正在做讲解和问答原型；愿意自行控制模型与资料配置，但不想从头完成所有管理页面。这些触发是待访谈验证的假设。

**采用条件：**能配置服务凭据和应用部署；可以承担 API 费用；对资料质量与目标语言做验收；接受已有界面，并有能力完成额外业务集成。

**为什么可能选择 OpenRealtime：**复用角色、资料、会话和呈现管理，加上独立组合语音与回答服务。实际节省的开发工作量尚未测量，应通过安装到完成场景的过程证明。

**会放弃的原因：**资料回答不可靠；配置过程中不清楚哪个服务失败；原有系统需要的嵌入、认证或接口没有清晰路径；成熟框架或单个供应商 SDK 更容易完成同一任务。

**文档必须提供：**一个小而完整的资料示例、导入与绑定步骤、预期问答、纠正和停止操作、配置清单，以及 Demo 模式和真实服务模式的区别。先写“知识讲解与问答”，上线客服与业务自动执行应另做验收。

### 2. 角色与数字人体验的创作者：第二条采用路径

**想完成的任务：**配置自己的声音、人设和形象，构建可持续交流的角色或演示应用。

[Open-LLM-VTuber 官方定位](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber)明确围绕语音、Live2D、跨平台与本地角色体验；记忆和工具请求显示该人群并非只看人物外观。OpenRealtime 已有角色、人设、素材和多种呈现方式，但不同路线的资源与效果并不相同。[数字人指南](../DIGITAL-HUMAN-DRIVING.md)

**更适合的子群：**接受浏览器入口与云 API、愿意配置人物素材的技术创作者和自部署爱好者。完全不愿配置服务的普通用户可作为在线体验者，不宜当成源码安装的首要对象。

**为什么可能选择：**通过已有界面组合角色、知识、声音和人物；可先纯语音，再选择云实时呈现或预生成动作。不能因此宣传所有路线都有实时逐字口型。

**会放弃的原因：**更需要桌面悬浮、Live2D、完全离线、细致的表情控制或成熟直播工作流；希望开源等于零 API 费用。上述需求应按当前支持逐项说明。

**文档必须提供：**角色创建步骤、人物路线选择、素材要求、声音与形象各自配置的位置、记忆与历史的区别，以及每条路线的成本构成。

### 3. 教学与训练角色扮演团队：有场景证据，交付仍需验证

**想完成的任务：**让学员反复与模拟客户、面试官或练习伙伴交流，而不是观看预录视频。

[Tavus 的 Berlitz 案例](https://www.tavus.io/customers/berlitz-spotlight)描述语言教育中的交互练习试点；[ACTO 案例](https://www.tavus.io/customers/acto-spotlight)描述行业知识与自有语言模型结合的角色扮演训练；[Anam 的 Glyphic 案例](https://anam.ai/case-studies/glyphic-interactive-avatars)描述销售练习与产品集成。这些供应商案例说明存在具体组织场景，不能证明 OpenRealtime 已有训练效果、同等交付或相同商业回报。

**为什么值得验证：**角色、资料、实时交流与可选形象，和练习流程有交集。相较纯资料问答，数字人是否产生额外价值更容易提出可测假设。

**当前缺口：**课程与练习编排、评估标准、教练反馈、班级或团队管理、机构系统集成；这些不因基础会话与角色界面存在而自动成立。外语学习还要求相应 ASR/TTS 与完整交流验收，不能从英文 README 推出。

**建议做法：**先做单个可配置角色的练习原型和小范围试用，明确哪些由提示词实现，哪些需要新增产品能力。现阶段不把本项目称为现成教学或企业训练平台。

### 4. 已有 Agent 的语音使用者：明确的需求，暂列后续采用方向

**想完成的任务：**对自己的编码或办事 Agent 说话，在任务执行时追问、补充要求，并听到结果。

[Qwen Audio Agent 官方仓库](https://github.com/QwenAudio/qwen-audio-agent)将桌面生产力与前台交流、后台工作作为重要路线；其[快速开始](https://qwenaudio.github.io/qwen-audio-agent/getting-started/quickstart)先完成一次语音对话，再增加后台 Agent。它表明该场景已有直接替代方案。

OpenRealtime 已有 ACP、Codex、Claude、Hermes 等适配基础，但[当前能力边界](../../README.md)仍将统一安装配置与完整任务体验列为 TODO。不能把“有适配文件”转换成“用户可以立即用语音完成自己的 Agent 工作”。

**升为首要受众的条件：**按一个具体后端给出完整安装、认证与连接路径；演示发起任务、追问进度、补充要求和返回结果；分清停止播放与取消任务；验证权限和会话恢复。这也是该人群的文档需求。

### 5. 语音框架工程师与研究者：扩展与贡献对象

**想完成的任务：**研究判停、附和、纠正与取消，替换供应商，诊断语音时序和故障。

[Pipecat](https://github.com/pipecat-ai/pipecat)和 [LiveKit Agents](https://docs.livekit.io/agents/)已有框架、客户端、工具与诊断生态；[LiveKit 数字人文档](https://docs.livekit.io/agents/models/avatar/)也提供多种呈现插件。不能只凭“插件化”“能打断”“有数字人”获得排他定位。

OpenRealtime 可吸引希望研究其具体运行时契约和 Web 集成的工程师，但该人群会要求可重复实验、清晰插件示例与准确的能力表。首屏介绍 Jev 或内部取消机制，容易让其他采用者误以为自己必须先学会这些才能使用产品。

**文档安排：**独立扩展路径，保留技术深度；先给一个最小适配示例，再链接协议、诊断和历史证据。Jev 作为可选决策组件介绍，不将单一模型品牌当作受众定义。

### 6. 电话、硬件与纯渲染用户：当前不优先招募

电话坐席需要 SIP、呼叫流程和部署体系；[LiveKit](https://docs.livekit.io/agents/)明确覆盖电话接入。设备用户需要真实采集、播放、重连与运维；本项目 [ESP32 客户端](../../clients/esp32/README.md)仍是参考示例。纯渲染与视频制作者主要关注模型、人物质量、制作和推流，可先比较 [LiveTalking](https://github.com/lipku/LiveTalking)与 [OpenAvatarChat](https://github.com/HumanAIGC-Engineering/OpenAvatarChat)。

这些人群并非没有价值，而是当前公开材料不足以承诺其核心任务。将其放在 README 首屏会增加支持预期与实际交付的距离。

## 优先级与最需要验证的假设

下表是定性决策，不是市场规模、付费意愿或客观评分。

| 候选受众 | 外部需求信号 | 与本地交付的衔接 | 当前建议 | 最需要验证 |
| --- | --- | --- | --- | --- |
| 知识与业务助手构建者 | 有具体应用请求 | 角色、知识、语音与 Web 管理可串联 | 第一优先级 | 现有界面是否减少其实际工作；资料问答是否达标 |
| 技术创作者、自部署角色爱好者 | 有角色、记忆与工具请求 | 人设、声音、素材和呈现入口已有 | 第二条路径 | 浏览器与云服务是否符合习惯；长期使用是否有价值 |
| 教学与训练产品团队 | 有供应商案例 | 基础交互可承接原型，业务流程需补充 | 小范围验证 | 数字人是否提升练习意愿；是否需要完整训练产品 |
| 已有 Agent 的语音使用者 | 有明确竞争产品与交互需求 | 适配基础存在，统一体验仍待交付 | 后续采用方向 | 完整任务协作与接入是否可复现 |
| 语音框架工程师 | 有框架生态与工程问题 | 合约和诊断路径可研究 | 扩展与贡献路径 | 示例、接口稳定性和实验是否足够 |
| 普通访客 | 可通过在线体验触达，尚无本项目数据 | 使用已配置服务，无需自行部署 | 体验入口 | 是否理解用途、完成对话并愿意复访 |
| 电话、硬件、纯渲染用户 | 有相关生态 | 核心交付要求与当前主路径不同 | 不作为首要受众 | 是否存在本项目确实更适合的具体任务 |

一个关键反证是：**许多采用者可能只需要供应商现成的 SDK 或托管工具。** [Anam 的演示工具](https://anam.ai/tools)已经以面试、销售练习、语言练习等任务提供直接体验；LiveKit 也有浏览器中的构建入口。如果用户只想得到一个可交流数字人，额外维护 OpenRealtime 不一定划算。

因此，本项目最值得验证的采用理由是：用户需要控制模型与资料组合、复用现有角色与资源工作区，并愿意自己运行和扩展应用。开源与自部署应用并不等于整个语音/数字人链路离线或没有供应商依赖。[云服务指南](../getting-started/CLOUD-SERVICES.md)

## 对 README、项目文档与前端页面的具体影响

### README：让构建者快速判断是否适合自己

建议首屏先用下面的具体描述帮助读者理解既有主张：

> 构建能自然交流的 AI 助手，配置自己的角色、知识、模型和声音，并按需接入数字人。

接着说明仓库包含可自行部署的 Web 应用与可扩展运行时。建议顺序为：产品与真实场景 → 体验入口 → 适合谁 → 首次运行 → 真实服务与数字人 → 能力状态 → 扩展与贡献。

三个候选示例按交付状态分开：产品资料讲解与问答作为首个可复现目标；自定义角色作为第二条路径；教学练习和外部 Agent 任务协作按验证结果分别列为示例或后续方向。每个示例给出预期结果，不能仅列行业名称。

### 项目文档：按采用阶段组织

建议主导航分为“认识产品”“开始体验”“构建自己的助手”“部署与维护”“开发与扩展”。对应入口包含：产品概览、场景与能力、页面使用、本地启动、真实服务、角色、知识、记忆、工具、数字人，以及部署和插件指南。

历史研究、架构决策与验证报告保持可查，通过技术和证据路径进入。首次使用者不需要先阅读所有研究材料。双语导航要明确正文语言，目标全球受众和实际语言验收分别说明。

### 前端文档：先服务正在使用应用的人

调研时的[前端目录](../../src/lib/public-documents.ts)将工具权限和多篇技术文章排在首页使用指南前，缺少产品概览、首次体验与配置顺序。整理后的首页已优先提供产品概览、资料问答示例、角色配置与可选数字人路径，另列部署和开发扩展。

构建者仍可从前端找到部署与扩展说明，但页面操作指南应优先可见。产品完善清单、审查规划和标签评估进入技术或研究分类。网站导航按任务命名，现有 `/docs/<slug>` 链接保留。Markdown 相对链接在仓库和站点中的解析也要在实施时核对。

## 后续用户验证建议

本轮未联系任何人。以下是建议的下一轮研究，不是已经完成的调查。

建议先邀请知识助手构建者、技术创作者和训练原型团队各 3–5 人，进行定性访谈与任务观察。人数是小样本研究建议，不能用来推算市场。

访谈重点问他们最近实际做过的事：

1. 最近一次想让助手用语音交流，具体要完成什么任务？给谁使用？
2. 已尝试了什么方案，卡在哪一步？投入了哪些开发和配置工作？
3. 哪些模型、知识、人物或系统必须保留自己的选择？原因是什么？
4. 语音和数字人分别解决什么问题？只用语音是否已经足够？
5. 是否愿意运行应用后端和购买服务？希望控制哪些数据与费用？
6. 什么结果会使他们第二次使用或向实际用户开放？

任务观察让参与者从 README 开始，用非敏感示例资料完成一次配置和对话；记录他们能否说清产品用途、找到入口、得到预期结果，以及需要帮助的位置。若需要额外凭据或付费服务，记录为真实门槛，不将已预配环境的时间混作全流程时间。

优先记录首次成功、配置失败点、资料问答结果、停止与纠正结果、是否愿意继续，以及数字人是否必要。阈值在试点前按任务商定；本轮不编造完成率或时长承诺。

如果构建者最终仍须重写大部分界面或无法复用自己的资料服务，第一优先级应重新评估；如果创作者表现出更强的重复使用，而业务团队只对演示感兴趣，则提高角色路径优先级；如果外部 Agent 完整交付后成为主要重复使用场景，再调整产品主张与 README。

## 讨论结论与后续补充

**建议：README 优先服务知识与可配置助手的构建者；前端文档优先服务体验者与角色配置者；项目文档通过部署和扩展路径承接技术采用者。**

这能保留全球开源定位，同时给三处文档不同的第一阅读任务。用户已确认首个上手场景为产品资料讲解与问答，产品首屏介绍完整的可自定义语音 Agent 能力；[配置指南](../getting-started/PRODUCT-ASSISTANT.md)与[产品概览](../getting-started/OVERVIEW.md)已按该方向整理。
