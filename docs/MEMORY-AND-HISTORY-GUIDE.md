# 知识库 Demo、Memory 与续聊

截至 2026-09-30，项目已具备知识检索、规则提取的长期记忆、当前会话上下文投影和断线恢复基础。历史记录页支持继续带有运行时标识的新记录；缺少标识的旧记录仍只供查看。跨服务重启续聊需要持久化 Journal。下面先用一个售后助手例子验证使用方式，再说明实际实现和缺口。

## 在页面里体验售后助手

### 1. 创建并绑定知识

打开[知识库资源页](/resources?tab=knowledge)，先选择准备体验的角色，填写名称「星河商店售后说明 v1」，粘贴以下正文并创建资料：

```text
星河商店的退货期限为签收后 7 天。
退货条件：商品未使用、包装完整，并提供订单号。
客服服务时间为工作日 09:00—18:00。
退货运费规则：商品质量问题由商店承担，其他情况由买家承担。
```

仓库也提供同样主题的 `docs/demos/shop-knowledge.md` 文件，可以直接选它导入。勾选资料，测试「退货期限」与「退货运费规则」，展开结果核对原文。

新资料会自动加入所选角色。进入[角色列表](/roles)，打开同一角色，在「知识库」中确认这份资料已选中。完整导入和更新方式见[知识库使用指南](/docs/knowledge-base)。

### 2. 添加一条长期记忆

在角色配置中启用「长期记忆」，再到[记忆管理](/resources?tab=memory)选择同一角色。添加一条「偏好」记忆：「我喜欢简洁回答」。

先手动添加可以确认记忆读取链路。自动保存则可另行测试：从这个角色开始对话，说「我的目标是学会日语」，等待对话记录保存后，重新打开 Memory 页面检查是否出现「目标」记录。页面不会自动刷新其他页面刚写入的记忆。

若列表未出现记录，请先查看[对话记录](/conversations)是否保存了这句话，确认该条用户消息是最终文本、角色记忆已开启，且使用同一账号与角色。自动提取失败不会让对话保存失败，也没有独立的页面失败提示。

### 3. 验证多轮上下文与记忆

从配置好的角色开始会话，依次问：

| 提问 | 要验证的内容 |
| --- | --- |
| 「请查知识库，星河商店的退货期限是多少？」 | 回答依据「签收后 7 天」 |
| 「我是因为商品质量问题退货。」接着问「那运费谁承担？」 | 前文的质量问题与当前知识片段结合，回答商店承担 |
| 「退款多久到账？」 | 资料缺少答案时明确说明，不猜时间 |
| 「我之前说过的学习目标是什么？」 | 在新会话中验证保存的目标记忆是否可读 |

前两轮测试当前会话上下文；最后一问测试跨会话的长期记忆。模型回答会有变化，要结合原文、Memory 列表和实际工具调用判断，不能仅凭一次回答看起来正确就认定链路完整。

### 4. 测试关闭和删除记忆

关闭该角色的长期记忆后，后续提示词不再注入这些记录，自动提取也停止。关闭不会删除已保存记录，需要在 Memory 页面单独删除或清空。

验证关闭是否生效时，使用一个新会话，避免模型仍从当前会话的前文读到同样内容。删除对话记录也不会自动删除由它提取的 Memory，两者分别管理。

## 无模型凭据也能运行的代码 Demo

在项目根目录执行：

```bash
.venv/bin/python -m demos.knowledge_memory_demo
```

Demo 使用临时目录和真实项目组件，运行结束自动清理，输出 JSON。它执行知识库工具检索、Memory 文件读取以及预算化上下文投影，展示传给模型的数据；无需启动网页、麦克风或调用付费模型。

验证结果包含：未绑定不命中、绑定后命中、用户隔离、新 Session 读取保存的 Memory、关闭后停止注入、同一 thread 读取前文，以及新 thread 不自动继承旧历史。

输出的模型输入类似：

```text
system_prompt:
  你是商店助手，请依据资料回答。
  <memory_data>我喜欢简洁回答</memory_data>

user_text:
  最近对话上下文：
  用户：我刚签收了星河商店的商品，想退货。
  助手：资料规定签收后 7 天内可以退货……
  当前用户输入：那运费谁承担？

knowledge_tool_result:
  [资料来源: 星河商店售后说明 v1]
  <untrusted_knowledge>退货运费规则……</untrusted_knowledge>
```

上面为简化展示；实际输出带 JSON 元数据。Demo 中的助手前文和 Memory 是预置测试数据，未运行自动提取、模型答案生成、浏览器续聊或 WebSocket 断线恢复。应与页面体验及各链路测试配合使用。

## Memory 实际怎么工作

长期记忆目前保存到 `.openrealtime/memory/memories.json`，可通过 `VOICEAGENT_MEMORY_DIR` 指定路径。每条记录包含用户、角色、类型、内容、来源对话 ID 和时间。

自动提取发生在网页调用 `POST /api/conversations` 保存记录时：服务端检查角色的 `memory_enabled`，取最后 5 条最终用户消息，对全文做正则匹配。不是后台语义归纳，也不是每轮语音事件都直接写入长期记忆。

| 类型 | 可触发的句式示例 |
| --- | --- |
| 偏好 | 我喜欢简洁回答、我不喜欢太长的解释、我偏好中文交流 |
| 目标 | 我的目标是学会日语、我打算长期学习编程 |
| 纠正 | 请记住我更喜欢分步骤说明、纠正一下称呼方式 |
| 关系 | 我和同事每周一起复盘 |

匹配针对整条消息，有长度限制，复杂句、多个事实、间接表达、否定或口语化改写可能不会保存。内容须满足敏感词与格式过滤；每条最多 300 字符，每个用户与角色最多 100 条，完全相同的内容会去重。

Python 的 `SessionMemory.apply()` 每次构造系统提示词时读取记录，检查角色开关，再选取当前用户和角色的最后 20 条，作为 `<memory_data>` 注入系统提示词。当前按 `updated_at`（缺失时用 `created_at`）选择最近 20 条，不按相关性检索；最近编辑的旧记录也会进入优先读取范围。没有时间戳的旧记录保留原相对顺序。

没有自动处理「原来喜欢 A，现在喜欢 B」之类的冲突。冲突条目需在管理页面编辑或删除。资料目录、记忆目录与角色配置目录需要在 Next.js 与 Python 进程之间共享，身份格式也必须一致。

## 历史如何进入模型

项目中有两种历史存储，用途不同：

| 数据 | 写入方与用途 | 是否直接供当前模型读取 |
| --- | --- | --- |
| 页面对话记录 | 浏览器收集 transcript，通过 `/api/conversations` 写入 `conversations.json`，用于列表与详情展示 | 可用来展示恢复前文；模型历史仍从经过授权的原 thread Journal 读取 |
| 服务端 Conversation Journal | 语音运行时记录用户输入、助手输出、工具结果等语义事件，按 tenant/user/thread 隔离 | 当前会话上下文来自这里 |

当前会话处理下一轮时，Cascaded Engine 获取当前输入之前的已投影 Journal 条目，通过 `BudgetedConversationContextProjector` 渲染历史，将其填入 `TurnContent.conversation_context`。`TurnContent.model_text` 再将历史和本轮输入组合，交给 Brain 与模型客户端。长期 Memory 通过系统提示词加入，知识库则由工具检索加入。

长历史有上下文预算与摘要压缩：预留输出、工具 schema、指令、当前输入和安全余量，达到阈值时压缩历史。摘要带源序列与摘要校验，不能随意替代原文；摘要 checkpoint 当前存在内存中。语音投影还区分已播放与被打断的输出，默认被打断的内容只保留确认听到的前缀。

## 「继续会话」需要区分使用场景

| 场景 | 当前实现 | 当前限制 |
| --- | --- | --- |
| 同一页暂停麦克风再恢复 | 停止/恢复输入，原连接与 thread 保持，前文可继续使用 | 依赖会话与连接仍有效 |
| 网络短暂断开后恢复 | 使用 session ID、resume token、序列号和恢复屏障重连 | 凭据在页面控制器内存中，刷新后不会直接复用 |
| 服务端要求创建 continuation | 控制器发送 `previous_voice_session_id` 和 `requested_thread_id`，服务端校验原 thread 权限 | 属于协议恢复链路，还不是历史页面的入口 |
| 结束后的当前页「继续」 | 本地复用当前 thread；公开准入续期发送原 session/thread 的 continuation | 服务端验证历史所属用户与原 session；历史不可用时拒绝，不静默降级成空会话 |
| 在历史详情页继续旧对话 | 新记录保存 thread/session 标识，详情页提供「继续此对话」；进入后点击「继续」开始 | 旧记录无标识不可恢复；已删除的角色不可恢复；运行时 Journal 必须仍存在 |
| 浏览器刷新或服务重启后继续 | Journal 可以配置 PostgreSQL 持久化 | 默认 `VOICEAGENT_STATE_BACKEND=memory` 不持久；网页历史存在磁盘不等于模型历史可恢复 |

页面记录 ID 仍为独立 UUID，同时保存 `thread_id` 与 `voice_session_id`，不保存 resume token。历史页面先按当前账号读取记录，服务端按记录选择原角色；运行时再验证 thread 归属和原 session 是否确实出现在 Journal 中。不会把网页上传的 transcript 直接当成模型历史，也不会将页面 UUID 当成 thread ID。

新建对话会重置运行时身份；本地连接重新握手，公开模式在下次准入创建新 thread。「继续」保留原 thread，并沿用同一页面记录 ID。跨 session 的历史展示去除旧 generation/turn 编号，避免新 session 使用相同编号覆盖旧消息。

恢复失败时需要检查账号、角色是否存在、运行时是否重启，以及 Journal 是否启用 PostgreSQL。默认内存后端无法在进程重启后恢复；旧记录缺少映射时也不能推测原 thread。此时可以新建对话并自行提供必要背景，但不等同于恢复原会话。

记录保存失败现在显示错误与「重试保存」按钮。保存仍有 800 ms 延迟，且采用浏览器排队写入，突然关闭页面可能丢失最后几条消息；恢复依赖的 Journal 由服务端独立记录。当前每条页面记录最多 500 条消息，超过时保存会报错。

## 完善程度与后续优先级

本次优化补齐了当前页结束后继续、新建 thread 隔离、运行时身份保存、历史详情续聊入口、旧消息编号隔离以及保存失败提示。

仍需继续完善：

1. **可靠保存**：服务端与页面记录同步、退出前刷写、超过 500 条消息时分页保存，以及 Memory 提取失败的可观察状态。
2. **旧记录迁移**：缺少 thread 标识的旧记录目前只读，没有自动推测身份或直接注入模型的隐式恢复流程。
3. **持久化验收**：线上使用 PostgreSQL 后验证跨刷新、跨进程重启、已过期 thread 和删除历史的行为。
4. **Memory 质量**：多事实提取、冲突替换、相关性筛选和来源查看，保留用户编辑与删除能力。

回归测试覆盖客户端握手与编号隔离、网页历史用户隔离及身份一致性、服务端 Journal 与恢复权限。未连接真实语音模型进行完整端到端验收，不能将这些测试视为模型实际回答效果的证明。
