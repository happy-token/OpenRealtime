01 / 06

架构总览

整体理念是「契约 + 能力插座」:VAD / ASR / TurnManager / Brain / TTS 都先定义为 Protocol(XxxCapabilityProvider.open() → XxxCapabilitySession),再由具体实现接入插座。 Turn Policy 作为独立的「仲裁层」挂在 TurnManager 旁,只做语义/状态判断,不直接碰音频。

级联式(Cascaded)引擎

server/realtime/cascaded/engine.py 是当前编排核心:ASR→EOT→LLM→TTS 逐级级联,每一级都是独立可替换的能力插座。server/realtime/native/ 下还有另一种 engine_kind(端到端原生引擎)与之并列,本手册聚焦级联架构。

Legacy 适配器模式

新契约大量通过 LegacyXxxCapabilityAdapter 包装旧实现接入插座—— 例如 EOT/打断判断的真正落点其实在 LegacyTurnManagerCapabilitySession 内部,而不是 TurnManager 契约本身。

02 / 06

消息流程:一次完整语音轮次

时间从上到下流动。四条泳道对应客户端、输入管线(VAD+ASR)、TurnManager(含 EOT 闩锁)、 会话引擎(控制面 + Brain + TTS)。虚线为回传/反馈路径。

关键数据结构:全链路由 InteractionContext 贯穿 (tenant_id / user_id / voice_session_id / thread_id / turn_id / generation / response_id), 几乎每条 command / event 都携带它;AudioFrame 则携带 stream_id / sequence / timestamp_us / duration_us / encoding / data。 所有用户输入与 assistant 输出都先落 Journal(ConversationItem) 再投影(ItemProjected)才允许触发响应或交付——Journal 是语义真相来源。

04 / 06

EOT 语义完整度判断机制

核心协调器是 SemanticEndpointGate(turn_policy/semantic_endpoint.py)—— 一个候选轮次只有同时拿到「语义锁」与「声学锁」才会真正提交。

三态结果与等待策略

状态后续动作
COMPLETE短文本立即收尾;长文本(≥60字)先等 long_text_grace_ms(默认200ms)宽限期,期间若检测到新语音则取消
INCOMPLETE发 transcript.incomplete 事件,保持话轮打开,incomplete_timeout_ms(默认5000ms)超时强制提交
UNCERTAIN按线性插值 wait_ms 短暂等待,裁剪在 [min_eot_ms, max_eot_ms] 区间内

活性兜底(防止话轮永不收尾)

  • ASR 空闲合成停顿:声学 VAD 仍判定在说话,但 ASR 文本已停止增长超过 asr_idle_stop_ms,则合成一个 VAD Stop 事件推动判断。
  • 绝对等待上限:以最近一次「实质 ASR 文本进展」为起点,设 max_open_ms(默认10000ms)绝对上限,专门应对 VAD 振荡(噪声反复触发 start/stop)导致的死锁。

分类器实现一览 turn_policy/plugins/*.py

分类器策略
PunctuationEotScorer纯规则:句末标点→COMPLETE,连接词结尾→INCOMPLETE,否则 UNCERTAIN。零网络开销,始终在线
LlmEotClassifier调用 LLM,要求输出 {status, confidence, wait_ms} JSON,支持流式边收边解析
FireRedChatEotProvider本地 ONNX 模型推理,线程池运行避免阻塞事件循环,阈值 0.5 二分类
FastCompleteFallbackEotClassifier两阶段:fast 判断「保守 COMPLETE」直接接受;否则转 fallback(通常是LLM),并对 fallback 结果做「悬空模式」否决(以连词/介词结尾强制改判 INCOMPLETE)
HybridEotClassifier并行多个证据源,consensus(全一致才采用,否则 UNCERTAIN)或 primary_with_shadow(主结果为准,其余仅记录)
EnsembleEotClassifierfast + slow 双评分器仲裁:分歧时降级为 UNCERTAIN,不允许单一信号独断;slow 超时(默认450ms)回退 fast
JevEotClassifier外部分类服务,confidence 低于阈值(默认0.8)降级为 UNCERTAIN

这些分类器可以互相组合(如 FastCompleteFallbackEotClassifier 本身又作为 SemanticEndpointGate.classifier 参数传入),项目没有强制统一到一种范式,取决于部署配置。

05 / 06

语义打断(Barge-in)判断机制

两层防护:先过滤 assistant 自己的回声,再对真实新语音做语义仲裁—— 区分「只是让它停」「要修正/补充」「只是附和」「与它无关的背景音」。

六类标签与动作

label含义停播生成新轮次
stop只要求停止,无后续任务(“别说了”)是否(丢弃该段输入)
correction修正已有条件或当前回答是是
interrupt回答助手提问 / 提出新任务是是
backchannel“嗯/好的”等支持性反馈否否
ignore回声/旁话/环境噪音/低证据短片段否否
uncertain证据不足,延迟判断否延迟决定

regex 规则优先,不等模型

精确停止短语("别说了"/"闭嘴")与附和词("嗯"/"好的")直接命中规则,不消耗模型调用预算,也不受调用延迟影响。

latest-wins 调度

新的 ASR revision 到达时取消上一个未完成的模型分类任务,只保留最新文本的判定结果——防止旧判定在新文本就绪前抢先放行。

fail-open 而非 fail-closed

模型超时(800ms)或异常时:有文本→INTERRUPT,无文本→IGNORE。宁可多打断一次,也不让系统卡死。

置信度阈值兜底

模型给出 stop 类标签但置信度低于 confidence_threshold(默认0.8)时,降级为 UNCERTAIN,不足以打断。

文本输入的硬性打断

RealtimeWebSocketFrameBridge._append_user_text() 处理用户直接发文本消息的场景: 无条件先 _cancel_active_response(reason="text_barge_in") 取消当前响应,再处理新文本—— 这条路径不走语义仲裁,是硬性打断,与语音打断的仲裁路径并列但独立。

06 / 06

延迟观测现状与建设建议

结论先说:协议层(响应/首字/首音)已有活跃打点,聚合查询能力(p50/p95/p99)已完整实现; 最大缺口是「打断延迟」和「EOT/打断分类器自身推理耗时」目前都没有真正写入遥测—— 契约已经定义好,只是没有接线。

现状盘点

层级 / 模块状态覆盖范围
协议层响应时序 活跃 RealtimeTelemetryObserver:response请求→首文字→首音频→终态,含 outcome 分类(OK/CANCELLED/TIMEOUT/ERROR)
供应商级 ASR/TTS 耗时 活跃 ProviderLatencyObserver + TimedAsrSession/TimedTtsSession,在 demos/voice_web_server.py 中已实例化并通过 provider_timing 参数接入
EOT 分类器推理耗时 部分预留 ClassifierEotEvidenceProvider.evaluate() 自带 inference_ms 字段,但未见转发进 telemetry
命名锚点时序(speech_started→playback_finished) 定义未接线 SessionTelemetry._capture_ledger_timing() 已设计好派生指标公式,但未发现任何 EventLedger.emit() 实际发出这些事件名
响应延迟里程碑(ResponseLatencyTrace) 定义未接线 LatencyMilestone 枚举与 VoiceLatencyTargets 目标值完整,但未发现 .mark() 的实际调用
打断延迟(检测→实际停止播放) 缺失 无任何实际记录;BARGE_IN_CONFIRMED/PLAYBACK_STOPPED 里程碑与 200ms 目标值仅存在于契约中
语义打断分类器推理耗时 缺失 SemanticInterruptionGate 内部有超时控制,但没有记录推理耗时
聚合查询(p50/p95/p99) 完整实现 DiagnosticsOverview / MetricAggregate,按指标名分组
按会话查询明细 完整实现 session_detail(),含完整事件列表

设计建议

纯函数式分段延迟计算

仿照 ResponseLatencyTrace.mark() 已有的「里程碑不可回退」校验,把每段延迟计算写成不可变快照上的纯函数:先校验相关时间戳是否严格单调递增,违反顺序就放弃上报而不是产出负数或污染统计。

统一的调用打点上下文管理器

SessionTelemetry.provider_call() 已经是这个模式(async with 包一层外部调用,出口无论成败都打一条结构化事件,outcome 归约到 ok/timeout/error/cancelled 等稳定小词表)——EOT 分类器与打断分类器的推理调用应直接复用同一套,而不是另起一套打点方式。

把"预留契约"接线,而不是新发明一套

LatencyMilestone/ResponseLatencyTrace 和 _capture_ledger_timing 的命名锚点协议已经把数据模型和派生公式设计好了,目前只是没人调用 .mark() 或 ledger.emit() 发出对应事件——最小的落地路径是接线,不是重新设计。

Generation 是延迟统计的边界

全链路已用 generation 做取消/替换的边界(打断会产生新 generation,旧 generation 的异步结果需要被丢弃)。打断延迟统计必须锚定在同一个 generation 上,否则会把过期事件误算进当前轮次。

新增 HTTP 接口建议(延续现有风格)

现有 control_plane/http.py 已有 DiagnosticsQuery 协议、统一 _write_json()、query 参数范围校验的写法,新接口应直接复用而不是另起一套:

建议路由用途
GET /observability/latency/overview?minutes=&prefix= 复用 DiagnosticsOverview,按指标名前缀(asr.*/tts.*/eot.*/barge_in.*)分组展示 p50/p95/p99
GET /observability/sessions/{id}/latency 单会话分段延迟明细:语义锁耗时/声学锁等待/首音延迟(对应 FTL 拆解),以及打断场景的检测→确认→停播三段计时

补齐缺口的具体落点

  1. 在 SemanticEndpointGate._classify() 与 SemanticInterruptionGate._classify() 内部,仿照 ClassifierEotEvidenceProvider 的 inference_ms 打点方式,补充调用 telemetry.record()。
  2. 在打断触发点(_request_assistant_yield)、CancelTts 实际发出点、客户端 client_playback_stopped 回传点三处打时间戳,拼出「检测→取消命令发出→客户端确认停止」三段延迟。
  3. 把 EotEvidence.inference_ms 这个已存在但未转发的字段接入 telemetry,是成本最低的第一步。
下一步:以上是现状梳理与设计建议,尚未改动任何代码。延迟统计功能涉及多处埋点与至少一个新接口, 属于非trivial的多文件实现——如果要继续,建议先过一遍实施计划(数据模型、埋点位置、接口契约)再动手。
