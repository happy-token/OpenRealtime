# 无独立 GPU 条件下的开源实时口型对齐方案调研

- 日期：2026-08-31
- 状态：技术选型建议，待同输入 A/B 验证
- 范围：预先生成动作视频，运行时只根据 TTS 音频修改口型
- 不在范围：图片/视频实时驱动整张脸、表情、头部和身体动作；该方向由另一项调研负责

## 结论

在“无 NVIDIA 独显、只使用开源方案、复用预生成动作视频、要求实时”这组约束下，当前没有一个已经验证过、能够无条件取代 Wav2Lip，同时在画质、通用性和实时性上全部更好的模型。

建议采用以下决策：

1. **以优化 Wav2Lip 96 为当前主线。** 当前 LiveTalking 路径在 Apple M1 MPS 上已经满足算力实时性，主要问题是 96×96 嘴部生成分辨率、人物裁剪和回贴效果，而不是模型吞吐不足。短期优先优化逐帧离线定位、裁剪、融合和静音闭嘴，风险和成本最低。
2. **DH_live_mini 2.0 不进入纯开源正式选型。** 它虽然与现有架构边界一致，仓库也声明 MIT，但自定义 Web 形象去 Logo 需要单独授权。项目要求无水印、无需商业授权时，它只能作为技术效果对照，不能作为默认产品路径。
3. **FeatherTalk 作为有条件的替代候选。** 它的运行时可使用 MNN 纯 CPU，且采用 Apache-2.0，但每个人物需要 3–5 分钟训练视频和一份专属权重，官方仍建议用 CUDA GPU 训练。只有在人物数量少、允许用 Apple MPS 试训或一次性借用/租用 GPU 时，才值得进入 PoC。
4. **MuseTalk 不作为无 GPU 本地主线，但保留为远程 GPU 质量档。** RTX 8000 实测已经跑通 MuseTalk 1.5 与 LiveTalking WebRTC 单路流式输出；官方 MuseTalk 稳态脚本达到 32.67 FPS，LiveTalking 实测约 25–29 FPS。不过首个有声包仍约 1.21–1.29 秒，且 LiveTalking 有水印声明和外部音频只支持整文件上传，正式接入需要自有 PCM 流式 sidecar。LatentSync、Zen-Dub 等更重路线本轮仍不投入，商业口型 API 也不在本轮范围。

严格来说，Wav2Lip 预训练权重只允许研究、学术和个人非商业使用，不属于宽松许可证意义上的完整开源资产。当前开源、非商业验证可以继续使用，但如果后续项目要商业化或公开分发模型权重，必须重新做许可证决策。

### 已实施的第一轮优化

2026-08-31 已将 LiveTalking 的整块人脸硬覆盖改为项目自有的轻量软融合模块：保留原动作视频的上半脸与裁剪框四周，只在嘴部/下半脸中心完整采用 Wav2Lip 预测，并在过渡区域使用平滑 Alpha。安装脚本会把该模块装入固定版本的 LiveTalking checkout，并分别校验补丁和合成模块 SHA-256。

本机验证结果：

- 96×96 单帧软融合平均约 0.158 ms。
- 10 秒 WebRTC 烟测约 25.39 FPS，后半段约 25.07 FPS。
- 相关 Wav2Lip/LiveTalking 测试 41 项通过，Ruff 检查通过。
- 单帧 A/B 可见软融合保留了原视频眼睛和上半脸细节，避免 Wav2Lip 96 把整个人脸一起模糊；嘴部本身仍受 96×96 模型上限约束。

这次烟测不等于正式实时验收，也没有证明口型准确度提升：仍需录制同输入完整视频，测图像级音画偏移并做盲测。下一轮优先处理离线逐帧稳定裁剪。

## 1. 问题边界

当前方案不是从一张照片实时生成完整数字人，而是：

```text
离线：人物素材 → 生成自然闭嘴的动作视频 → 预处理并缓存人物资产
在线：流式 TTS 音频 → 口型模型 → 只替换嘴部/下半脸 → 与原动作视频合成 → WebRTC 输出
```

这种方案的限制是人物动作不能即时响应语义，但优势也很明确：

- 动作视频只生成一次，可跨会话复用，生成成本可以摊薄。
- 运行时只计算小范围人脸区域，不需要扩散模型持续生成完整画面。
- 保留原视频的身体、头部、背景和大部分面部细节，失败面更小。
- 可以在本机或用户浏览器运行，不产生按分钟的口型 API 费用。

本项目规格已经采用这一边界：LivePortrait 只生成自然闭嘴、无音轨的动作底片，实际回复音频由后续口型模型单独处理。参见[数字人工作台规格](../specs/digital-human-workbench.md)。

## 2. 当前 Wav2Lip 基线

项目当前默认的分段式口型模型是 `wav2lip96`，运行时准备逻辑也固定接入 LiveTalking Wav2Lip。参见 [avatar-session-config.ts](../../src/lib/avatar-session-config.ts) 和 [avatar-renderer-preparation.ts](../../src/lib/avatar-renderer-preparation.ts)。

### 2.1 已经满足的部分

项目现有[评测数据](../../research-assets/avatar-evaluation/2026-08-22/benchmark.csv)显示：

| 场景 | 设备 | 输入 | 计算/播放结果 | 结论 |
| --- | --- | ---: | ---: | --- |
| LiveTalking Wav2Lip 96 | Apple M1 MPS | 20 秒 | 计算 7.951 秒，RTF 0.398，平均推理 62.885 FPS | 生成吞吐有实时余量 |
| LiveTalking 10 分钟 WebRTC | Apple M1 MPS | 600 秒 | 输出约 25 FPS，无接收帧缺口 | 长时间播放基本稳定；尚未测可见首帧和图像级 AV 偏移 |
| 官方离线脚本，逐帧 S3FD 检测 | Apple M1 MPS | 3.12 秒 | 339.684 秒 | 人脸检测完全不可用于在线链路 |
| 官方离线脚本，固定人脸框 | Apple M1 MPS | 3.12 秒 | 4.268 秒，其中生成 1.83 秒 | 预计算人物区域是决定性优化 |

这里的 MPS 是 Apple Silicon 集成加速，不是独立显卡。若目标机器是纯 x86 CPU，这组数字不能直接外推，必须再做 OpenVINO/ONNX Runtime CPU 实测。

### 2.2 效果不好的主要原因

- 官方 Wav2Lip 将人脸裁剪到 **96×96** 输入；嘴部在最终 720p/1080p 画面中被放大后容易模糊。
- 口型网络只生成局部，最终观感高度依赖人脸框、下巴 padding、颜色匹配、遮罩羽化和回贴策略。
- 检测框逐帧抖动会表现为嘴部漂移；过度平滑又可能形成双嘴或口型跟随滞后。官方也建议分别调整 `pads`、`nosmooth` 和输出分辨率。
- 动作底片若本身张嘴、快速转头、遮挡嘴部或光照变化大，会放大融合问题。

因此，“Wav2Lip 效果差”需要拆成两类验证：模型生成的嘴形/纹理本身差，还是工程回贴和底片素材造成的差。两者对应的解决方案不同。

### 3.1 DH_live_mini 2.0：仅作为技术对照

它在技术形态上很贴合需求：输入仍然是一段预生成的人物视频，离线制作人物资产，在线在浏览器按音频驱动嘴部，不需要接管完整的人物动作生成。

官方仓库在 2026-05-12 更新到 mini 2.0，列出的指标是 52 MFLOPS/帧、184 脸部区域、无需训练，并声明网页、App 和小程序均可运行。2026-08-16 又移除了 MediaPipe 依赖。项目内 v1 使用同一 Shuchang 动作底片和固定音频，已在 Apple M1 浏览器稳定到约 25 FPS；不过现有结果仍带 MatesX 水印，而且没有完整的图像级 AV 偏移和主观画质结论。

主要风险：

- 需要重新用 mini 2.0 制作当前人物资产，不能拿 v1 的效果代表 2.0。
- 仓库声明 MIT，但 Web 形象去 Logo 仍有单独授权说明；“代码开源”和“无品牌限制地发布自定义人物包”不是同一件事。该条件直接阻止它进入本轮正式选型。
- 当前项目对比的是 v1，迁移 2.0 可能涉及 Web/WASM 资源格式和渲染接口变化。
- 184 的区域分辨率高于 Wav2Lip 96，但分辨率更高不等于实际口型一定更准，必须做同底片、同音频盲测。

### 3.2 FeatherTalk

FeatherTalk 的视觉输入为 144×144，约 5.46M 参数；最新仓库提供 FeatherHuBERT 音频编码器、ONNX 导出和 C++/MNN 路径，运行时可不依赖 Python、PyTorch、OpenCV 或 ONNX Runtime，并能选择 CPU、Metal 或 OpenCL。

它可能在固定人物上获得比通用 Wav2Lip 更稳定的口型和融合效果，但代价是每个人物都要训练：

- 推荐素材为 3–5 分钟、25 FPS、清晰单人口播视频。
- 每个人物生成一份专属 checkpoint/ONNX/MNN 模型。
- 官方建议用 CUDA GPU 训练；当前训练代码也会自动选择 Apple MPS，纯 CPU 只在显式增加 `--allow_cpu` 后运行，官方没有给出 MPS/CPU 训练耗时。
- 截至官方 `fdccc3c`（2026-08-28），Python 与 C++/MNN 都只提供离线文件推理；旧搜索索引中的 `dihuman_run.py` 已从当前仓库移除。改成流式需要自行实现 PCM 缓冲、增量音频特征、逐帧输出和中断控制。
- 每帧使用约 800 ms 的中心音频窗口，完整保留当前上下文会产生约 360–400 ms 的前视等待，吞吐实时和交互低延迟必须分开验收。

如果未来只维护少量固定数字人，这是一条值得验证的低运行成本路线；如果用户可以不断上传新人物，它的逐人训练成本会成为硬门槛。

完整使用命令、动作底片准备方式、MNN 部署和实时改造边界见 [FeatherTalk 使用方式与 OpenRealtime 接入评估](./2026-08-31-feathertalk-usage-and-integration.md)。

### 3.3 Wav2Lip GAN 与运行时优化

Wav2Lip 官方同时提供普通和 GAN checkpoint。官方描述是：GAN 版本视觉质量更好，但口型同步准确度略差。它不解决 96×96 的上限，也不改变许可证，但可以作为最低成本的 A/B 组，不需要重做整个运行时。

在 Intel CPU 上，可以尝试把 Wav2Lip 导出 ONNX 并用 OpenVINO；在 Apple Silicon 上继续比较 PyTorch MPS、Core ML 和 MNN。它们只是推理后端优化，不是新口型模型，最终是否有收益必须以目标机器实测为准。

### 3.4 MuseTalk + LiveTalking 远程 GPU 实测

本轮已在 Quadro RTX 8000 48 GB 上跑通 MuseTalk 1.5 官方 Demo 和 LiveTalking WebRTC：

- 官方 MuseTalk 使用缓存 avatar、跳过 PNG 保存时，60 秒音频生成 1500 帧耗时 45.907 秒，即 32.67 FPS。
- LiveTalking 确实按 20 ms PCM 块在进程内做增量特征和推理，并通过 WebRTC 持续输出 25 FPS 画面，不是生成完整 MP4 后再返回。
- 预先把输入统一为 16 kHz 单声道后，HTTP 音频处理从约 1.05 秒降到 7–36 ms；但提交到首个有声包仍约 1.21–1.29 秒。
- LiveTalking 的 `/humanaudio` 仍要求上传完整文件，不是外部 PCM 流；正式接入 `AudioDelta` 需要新增 WebSocket/gRPC 音频入口。
- LiveTalking 源码无条件写入水印，README 还要求公开视频保留水印和 Logo，因此不能在要求无水印时直接作为正式运行时。

完整环境、吞吐、WebRTC 证据、流式边界和接入建议见 [MuseTalk + LiveTalking GPU 流式验证报告](./2026-08-31-musetalk-livetalking-gpu-streaming-validation.md)。

## 4. 推荐落地方案

### 阶段 A：先定位画质问题

先为同一段 5 秒测试素材输出四宫格调试视频：原始全帧、原始人脸裁剪、Wav2Lip 96×96 输出、最终回贴画面。每帧同时保存人脸框、关键点和融合遮罩。这样可以区分：

- 96×96 输出本身已经模糊或牙齿异常：属于模型上限，可比较 GAN checkpoint 或 FeatherTalk。
- 96×96 输出可接受，但最终画面出现漂移、色差或双嘴：属于裁剪、跟踪和融合问题，应先修工程链路。
- 只在转头或循环边界变差：属于动作底片及逐帧定位问题。
- 静音时嘴仍抖动或不能闭合：应加入静音旁路，而不是继续平滑模型输出。

不能简单把 `img_size` 从 96 改成 256。官方 checkpoint 的网络结构和训练分辨率固定为 96×96；直接修改参数不能得到真正的高清 Wav2Lip，通常会导致权重维度不匹配或仅做无信息的放大。

### 阶段 B：优化人物资产预处理

对每个动作视频离线生成一份 `prepared avatar` 资产：

- 固定帧率为 25 FPS，并保存无音轨版本。
- 使用高质量人脸关键点/跟踪器离线计算**每一帧**的人脸仿射变换，不在线运行检测器。
- 以眼睛、鼻尖和嘴角稳定裁剪区域，使嘴部在 96×96 输入中的位置和大小尽量恒定；保存每帧逆变换用于回贴。
- 预计算每帧人脸框、关键点、嘴部 ROI、融合遮罩和颜色统计。
- 缓存已裁剪的人脸帧及模型需要的张量，在线阶段不再运行 S3FD。
- 素材准入限制为自然闭嘴、嘴部无遮挡、转头角度有限、曝光稳定。
- 模型常驻并预热；音频到达后只做特征、口型推理和回贴。

项目现有 `prepare_livetalking_avatar.py` 已经支持固定人脸框并缓存 96×96 人脸帧，这是速度优化的正确起点；但一个固定框不能跟随头部移动。下一步应把它升级为“离线逐帧关键点跟踪 + 稳定裁剪”，而不是恢复在线 S3FD。项目实测中，跳过在线 S3FD 已使 3.12 秒素材从 339.684 秒降到 4.268 秒。

### 阶段 C：优化回贴与静音状态

Wav2Lip 的最终观感很大程度来自合成，不建议把整个预测人脸矩形硬覆盖回原视频：

- 根据嘴角、上下唇和下巴关键点生成下半脸多边形遮罩，只替换嘴部及必要的下颌区域，保留原视频的眼睛、鼻子和皮肤纹理。
- 在原视频分辨率上做 8–16 像素的边缘羽化；数值按脸部宽度等比例调整，避免固定像素适配所有分辨率。
- 从遮罩外圈估计亮度和颜色差，只对预测区域做轻量颜色匹配，避免整帧调色。
- 只平滑人脸变换和融合残差，不长窗口平均最终嘴形；否则会造成发音滞后和双嘴。
- 当音频 RMS/VAD 连续约 100–160 ms 判定为静音时，旁路 Wav2Lip 输出并回到动作底片的原始闭嘴区域；恢复说话时做 2–3 帧短过渡。
- 对动作视频首尾做闭嘴帧筛选和短交叉淡化，避免循环点突然改变嘴形或人脸位置。

轻量锐化可以作为最后一步小范围尝试，但 GFPGAN、CodeFormer 或逐帧超分在无独显环境中通常会吃掉实时余量，而且不能修复错误口型，因此不应放在主链路。

### 阶段 D：做同输入 A/B

固定同一人物、同一动作底片和同一段测试音频，只更换口型链路：

1. 当前 Wav2Lip 普通 checkpoint，作为原始基线。
2. 普通 checkpoint + 逐帧稳定裁剪 + 局部软遮罩 + 静音闭嘴。
3. 相同工程参数下的 Wav2Lip GAN checkpoint。

DH_live_mini 只在接受带 Logo 的内部技术比较时作为第四组，不进入发布决策。FeatherTalk 不放入第一轮；只有前三组仍不能达到质量要求，并且确定人物数量有限、允许一次性训练时，再增加 FeatherTalk。

测试音频至少包含：

- 中文双唇音和爆破音，如“爸爸、苹果、明白、发布”。
- 快速连续语句、慢速拖音、低音量片段。
- 句中停顿和结尾至少 1.5 秒静音，用于检查自然闭嘴。
- 底片循环边界、轻微转头和不同光照帧。

### 阶段 E：优化流式运行时

- 以 4–8 帧为一个小批次；25 FPS 下对应约 160–320 ms 音频窗口。
- TTS、口型推理和发送并行流水化，不等待整句音频完成。
- 使用音频时钟作为主时钟，视频帧可丢弃但音频不可被视频计算阻塞。
- 中断时立即清空待生成和待发送帧，并切换到闭嘴底片帧。
- 回贴采用边缘羽化、轻量颜色校正和有界时序平滑；不得用长窗口平滑掩盖抖动。

项目当前 LiveTalking 基准使用 `batch_size=4`，对应约 160 ms，适合作为延迟基线。增加批量可能提高吞吐但会增加首个可见嘴形的等待时间；当前算力已有余量，不应为了更高离线 FPS 牺牲交互延迟。

### 优先级汇总

| 优先级 | 优化项 | 主要收益 | 是否影响实时性 |
| --- | --- | --- | --- |
| P0 | 四宫格调试输出，定位模型还是融合问题 | 避免错误优化方向 | 仅评测使用 |
| P0 | 离线逐帧关键点跟踪、稳定裁剪、缓存逆变换 | 减少嘴部漂移和裁剪跳动 | 在线更快 |
| P0 | 嘴部/下半脸软遮罩、颜色匹配 | 减少边界、色差和塑料感 | 很小 |
| P0 | 静音旁路和闭嘴过渡 | 修复停顿不闭嘴、抖动 | 在线更快 |
| P1 | 普通 checkpoint 与 GAN checkpoint A/B | 比较同步准确与视觉清晰 | 吞吐需实测 |
| P1 | MPS / OpenVINO / MNN 后端比较、模型预热 | 提高纯 CPU/集成加速性能 | 正向 |
| P2 | 逐帧超分或人脸修复 | 可能锐化纹理 | 无独显时大概率不实时 |

## 5. 建议验收门槛

以下是项目建议值，不是各模型官方承诺：

| 维度 | 建议门槛 |
| --- | ---: |
| 稳态输出 | 25 FPS |
| 口型计算 RTF | ≤ 0.8，保留至少 20% 抖动余量 |
| 音频块到首个可见嘴形变化 | p50 ≤ 400 ms，p95 ≤ 700 ms |
| 图像级音画偏移绝对值 | p95 ≤ 80 ms |
| 中断到可见闭嘴 | p95 ≤ 250 ms |
| 10 分钟稳定性 | 无持续队列增长、无接收帧缺口 |
| 主观画质 | 同输入盲测相对当前 Wav2Lip 获得 ≥60% 偏好 |

主观评分要分别记录口型准确、嘴部清晰、牙齿/唇纹自然、边界融合、非嘴区域稳定和静音闭嘴，避免用一个“效果好不好”总分掩盖问题来源。

## 6. 成本判断

| 路线 | 一次性成本 | 运行成本 | 扩展成本 |
| --- | --- | --- | --- |
| 优化 Wav2Lip | 每段动作视频预处理 | 本机 CPU/MPS，无按分钟费用 | 新人物无需训练，只需预处理 |
| DH_live_mini 2.0 | 每段视频制作 Web 人物资产 | 用户浏览器 CPU/WebGL/WASM，无口型 API 费用 | 新人物无需训练；需确认 Logo/人物授权 |
| FeatherTalk | 每个人物准备素材并训练 | MNN CPU，可保持很低 | 人物越多，训练和模型管理成本越高 |
| GPU 模型/API | GPU 部署或按量调用 | 持续 GPU/分钟费用 | 并发增长时成本线性上升 |

因此，当前“预生成动作视频 + 轻量口型”的思路是合理的低成本架构。它不追求实时生成完整动作，而是把昂贵计算前置并复用，适合人物动作可模板化、成本优先的场景。

## 7. 最终建议

短期不要删除 Wav2Lip，也不要为追求画质直接转向 MuseTalk/LatentSync。实施顺序建议为：

1. 为当前 Wav2Lip 增加可视化诊断，先确定问题来自模型还是融合。
2. 将固定框资产升级为离线逐帧稳定裁剪，并加入嘴部软遮罩、颜色匹配和静音闭嘴。
3. 在相同工程链路下比较 Wav2Lip 普通与 GAN checkpoint，按画质和同步指标选择默认权重。
4. DH_live 只保留为带 Logo 的内部技术样本，不作为纯开源发布候选。
5. 如果优化后的 Wav2Lip 仍不满足画质，先用远程 MuseTalk 做同底片质量 A/B；正式接入使用自有 PCM 流式 sidecar，避免依赖 LiveTalking 的水印和整文件音频 API。
6. 如果人物数量固定、希望长期降低 GPU 运行成本，再训练 FeatherTalk 并验证 MNN；训练需要一次性 GPU 资源。
7. 等独立的“实时人物驱动”调研完成后，只在产品层比较两种架构的效果与成本，不在本口型模块中混入头部、表情和身体驱动逻辑。
