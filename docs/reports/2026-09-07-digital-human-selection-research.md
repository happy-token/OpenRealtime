# 数字人驱动方案选型指南

更新日期：2026-09-07。面向希望在网站、助手或对话产品中加入数字人的用户。本文按交付方式分为 **端到端实时驱动、多段式合成、预生成动作编排**，比较效果、成本、硬件和适用场景。

本文的“端到端”指用户可以直接接入的完整实时服务，不限定供应商内部模型架构。“多段式”指动作、面部运动、口型等环节分别制作或合成，不是把回复切成几段播放。调研覆盖官方产品、开源仓库、论文项目页，以及本地 LiveTalking、OpenTalking 和 OpenRealtime 实现；没有对全部候选重新做效果实测。

## 先选路线，再选模型

| 你的需求 | 优先路线 | 需要付出的成本 | 得到什么 / 接受什么 |
| --- | --- | --- | --- |
| 想快速上线，重视真人说话效果，不想维护模型 | **端到端实时驱动** | 持续的 API 会话费用 | 获得实时口型与人物表现；依赖供应商、网络和套餐 |
| 想自部署、控制人物动作或改善口型，有开发和算力条件 | **多段式合成** | 模型集成、人物预处理、GPU 或端侧适配 | 控制空间大；效果和实时性依赖具体模型及素材 |
| 没有专用 GPU，希望低成本、响应快、有动作且嘴巴会动，允许不逐字对口型 | **预生成动作编排** | 一次性动作素材制作、存储与分发 | 待机与讲话状态自然切换；讲话嘴形不匹配每个音素 |

**针对“无专用 GPU、低成本、不要只显示一张静态图片”的需求，建议优先试预生成动作编排。** 将资源用于好看、连贯的动作素材和及时的状态切换，通常比勉强运行低质量口型模型更符合这组目标。这是针对约束条件的选型建议，实际效果仍应由目标用户验证。

## 一、端到端实时驱动：直接接 API，持续付费

### 适合谁

适合希望快速交付实时数字人，愿意用服务费换取人物生成、口型、媒体输出与部署维护的团队。重点候选是 **Anam 和 HeyGen 的 LiveAvatar**；可同时比较 Tavus、D-ID、Simli、LemonSlice、Runway Characters。

这类服务的选型价值在于较完整的人物表现和集成体验。是否“效果好”，要看你的角色、语种和网络条件，不能把供应商演示当作所有场景的保证。与只播放预制动作相比，它们有持续会话成本；与低利用率、长期常驻的 GPU 服务相比，API 未必更贵。

### 怎么预算

月成本可以按“套餐月费 + 超出包含量的会话分钟 × 超额单价 + 自带语音/模型/网络费用”估算。LiveAvatar 要先选择 FULL 或 LITE。用量不足时，套餐均摊价会更高；只在数字人说话时计时，可能低估实际账单。

例如，在相同套餐与上述价格不变的假设下：

| 每月 1,000 个计费会话分钟 | 算术示例，不代表跨产品效果等价 |
| --- | --- |
| Anam Explorer | $49 + 750 × $0.14 = **$154** |
| LiveAvatar Essential LITE | 额度内，**$99**，自带语音/对话费用另加 |
| LiveAvatar Essential FULL | $99 + 450 × $0.19 = **$184.50** |
| Runway Characters | 持续时长约 **$200**，另加会话数 × $0.02 启动费；按 6 秒计费区间核算 |

## 二、多段式合成：控制空间大，素材与算力决定结果

这类方案把“人物怎么动”和“嘴怎么跟随音频”拆开处理，或用多个模型依次生成运动和画面。开源的主要价值是可自部署和可调整，不代表零成本，也不保证画质自动优于托管服务。

### 三类合成路线

按**口型对齐之前，人物画面由什么驱动**，可以分为以下三类。它们都可以从一张人物图片开始，区别在于运行时使用静态图、完整动作底片，还是单独控制面部运动。

| 子路线 | 工作方式 | 主要动态来自哪里 | 典型案例与定位 |
| --- | --- | --- | --- |
| **1）图片驱动 + 口型对齐** | 人物图片 + 回复音频 → 嘴部合成 → 说话画面 | 主要是嘴部，其他区域基本保持原图 | 常见的照片开口、照片播报、静态人像语音助手；图片接 Wav2Lip / MuseTalk |
| **2）动作驱动 + 口型对齐** | 实拍或预生成动作视频 + 回复音频 → 改嘴并回贴 → 完整人物画面 | 底片提供身体、头动、背景和已有表情 | LiveTalking、OpenTalking 的典型视频模板链路；数字主播、讲解员、带动作的陪伴角色 |
| **3）面部动作驱动 + 口型对齐** | 人物图片 + 面部运动/表情控制 → 动态人脸 → 按回复音频对齐口型 | 单独驱动眨眼、视线、微笑、点头等，再协调嘴形 | AI 赛博女友、近景陪伴人像等重视表情反馈的体验；LivePortrait 类面部驱动配合口型模块 |

这是一种面向选型的工作流分类，不是对市场占比的统计。LiveTalking、OpenTalking 都支持多种模型，不能将整个框架限定为第 2 类；“AI 赛博女友”也是应用场景名称，可能采用不同技术路线。

### 1）图片驱动 + 口型对齐：让照片开口

**案例：上传一张人物照片，让它朗读文字或回复问题。** 图片提供人物身份和构图，TTS 生成语音，再用 Wav2Lip 或 MuseTalk 按音频生成嘴部画面。这里描述的是图片作为固定底图的用法，不包括模型另外生成头动和表情的情况。[Wav2Lip](https://github.com/Rudrabha/Wav2Lip)、[MuseTalk](https://github.com/TMElyralab/MuseTalk)

素材准备最简单，不需要先拍摄或生成动作视频；但如果只有嘴在动，长时间近景对话容易显得僵硬。适合照片播报、简单导览和低素材门槛的原型。常见“照片说话”工具可以先按这一类理解，具体工具若额外生成面部运动，则应归入第 3 类或独立生成式路线。

### 2）动作驱动 + 口型对齐：让已有动作说新内容

**案例：数字讲解员保持自然呼吸、转头和手势，同时说出每次新生成的回答。** 先准备一段完整的人物动作视频；对话时复用底片，用新音频替换嘴形，身体和大部分画面沿用素材。

**LiveTalking、OpenTalking 是这一类的典型框架参考。** LiveTalking 的 Wav2Lip / MuseTalk 人物视频资产，以及 OpenTalking 的 QuickTalk 模板视频路线，都适合用“动作底片 + 音频口型”理解。OpenTalking 也支持静态参考图及 FasterLivePortrait / JoyVASA 等其他路线，选型时要看具体配置。[LiveTalking](https://github.com/lipku/LiveTalking)、[OpenTalking](https://github.com/datascale-ai/opentalking)

这类比固定图片有更多自然动作，素材也能反复使用；代价是要准备动作视频，且点头、手势不一定符合当前回答语义。**只要说话时仍按新音频计算嘴形，它就是多段式合成；如果完全不改嘴，只切换预制待机/讲话视频，就属于本文第三大类“预生成动作编排”。**

### 3）面部动作驱动 + 口型对齐：让表情与说话共同表现

**案例：AI 赛博女友 / 陪伴人像。** 想要的体验通常不只是张嘴，而是倾听时眨眼、注视，回应时微笑、歪头、点头，再配合当前语音的嘴形。针对这种以近景人脸和表情交流为重点的需求，可优先考虑这一类。

一个可组合的参考工作流是：人物图片 → LivePortrait / FasterLivePortrait 驱动表情与头部 → MuseTalk / Wav2Lip 对齐回复口型。面部运动可以来自驱动视频、预设运动模板或表情参数；例如 ComfyUI-AdvancedLivePortrait 提供表情编辑与运动组合能力。这里是**基于公开模块的组合案例**，不是声称某个未公开实现的赛博女友产品一定采用了这些模型。[LivePortrait](https://github.com/KlingAIResearch/LivePortrait)、[FasterLivePortrait](https://github.com/warmshao/FasterLivePortrait)、[AdvancedLivePortrait](https://github.com/PowerHouseMan/ComfyUI-AdvancedLivePortrait)

另一种方式是用 JoyVASA 等模块从音频生成面部和头部运动，再由肖像模型渲染。若驱动链路已经生成与语音匹配的嘴形，“口型对齐”可以由内部模块完成，不必强制再串一次 Wav2Lip；单独改嘴还可能破坏微笑等表情，需要对嘴部控制做协调。[JoyVASA](https://github.com/jdh-algo/JoyVASA)

与第 2 类相比，关键是**面部运动能单独控制**，不只是重播一段完整动作底片。若先离线生成面部动作、保存成视频，在线只循环底片再改嘴，那么按在线使用方式仍属于第 2 类。第三类的表情空间更大，但调度、融合与算力需求也更复杂。

### 主要开源模型扫描

下表硬件与速度来自上游资料，条件不同，**不能直接当作横向跑分**。“离线”表示更适合先生成成片或动作素材；播放生成好的视频并不需要继续运行生成模型。

| 模型/组合 | 主要能力 | 实时性与资源 | 选型判断 |
| --- | --- | --- | --- |
| [Wav2Lip](https://github.com/Rudrabha/Wav2Lip) | 保留视频动作，替换口型 | 原项目以文件推理为主；需框架封装流式、预处理与播放 | 成熟基线；原版嘴部细节有限，原开源模型有非商用限制 |
| [MuseTalk 1.5](https://github.com/TMElyralab/MuseTalk) | 潜空间口型合成，256 脸区 | 官方在 Tesla V100 宣称 30+ FPS，需人物预处理与缓存 | GPU 口型质量对照首选之一；仍依赖素材、人脸框与融合 |
| [LatentSync 1.6](https://github.com/bytedance/LatentSync) | 扩散式口型重建 | 官方最低推理显存 18 GB；1.5 为 8 GB | 更适合离线配音对比，不按开箱实时通话推荐 |
| [LivePortrait](https://github.com/KlingAIResearch/LivePortrait) / [FasterLivePortrait](https://github.com/warmshao/FasterLivePortrait) | 参考图 + 动作视频，迁移表情头动 | Faster 版官方称 3090 + TensorRT 30+ FPS；这只是运动到画面的渲染链路 | 很适合制作动作底片；自身不会自动把任意新语音转成正确嘴形 |
| [JoyVASA + LivePortrait](https://github.com/jdh-algo/JoyVASA) | 音频生成头动与面部运动，再渲染 | 官方测试含 A100 和 4060 Laptop 8 GB | 必须测完整链路，不能把渲染器 FPS 当成整条语音驱动速度 |
| [Ditto](https://github.com/antgroup/ditto-talkinghead) | 音频 → 运动 → 肖像渲染 | 官方提供 online/offline 路径，测试环境含 A100/TensorRT | 值得进入自部署实时候选，部署和端到端延迟仍需验证 |
| [SadTalker](https://github.com/OpenTalker/SadTalker) | 照片 + 音频 → 3D 运动系数 → 视频 | 以离线生成工作流为主 | 照片开口基线；不等于实时会话产品 |
| [EchoMimicV2](https://github.com/antgroup/echomimic_v2) | 半身图 + 音频 + 姿态，加入手势 | 官方加速版 A100 约 50 秒生成 120 帧 | 适合离线制作有身体动作的素材，不是实时生成 |
| [InfiniteTalk](https://github.com/MeiGen-AI/InfiniteTalk) | 图片/视频 + 音频，联动口型、头动与身体 | 14B 基座，提供多 GPU/量化路线 | 适合长视频素材；其 streaming 指分块长视频生成，不能直接等同于实时通话 |
| [Sonic](https://github.com/jixiaozhong/Sonic) | 照片 + 音频生成富表现力人像 | 官方测试 NVIDIA 单卡 32 GB，非商用限制 | 研究/离线效果对照，不作为商业自部署默认选择 |

[Hallo2](https://github.com/fudan-generative-vision/hallo2) 和 [AniPortrait](https://github.com/Zejun-Yang/AniPortrait) 也是离线人像或动作素材候选。若目标是即时对话，应先筛掉无法以音频产生速度持续输出的方案，而不是先比较最漂亮的离线示例。

### 不应遗漏的轻量方案

| 方案 | 低运行成本来自哪里 | 要付出的其他代价 |
| --- | --- | --- |
| [FeatherTalk](https://github.com/anliyuan/FeatherTalk) | 小模型，官方提供纯 CPU 的 C++/MNN 路径 | 每个人物训练专属模型，推荐 3–5 分钟口播素材、CUDA 训练；默认文件推理，流式仍需适配 |
| [DH_live mini / mini2.0](https://github.com/kleinlee/DH_live) | 官方提供浏览器/移动端无专用 GPU 的轻量口型路径 | 需制作专用人物资产；网页去 Logo 有单独授权条件，设备与人物效果需验证 |

因此，“多段式一定要在线 GPU”不准确。更实用的判断是：**通用、高质量人像合成通常需要较强算力；端侧轻量方案通过较小模型、专用资产或人物训练来换取低运行成本。**

### 实时生成模型是另一组自部署候选

[SoulX-FlashHead](https://github.com/Soul-AILab/SoulX-FlashHead) 和 [SoulX-FlashTalk](https://github.com/Soul-AILab/SoulX-FlashTalk) 直接根据肖像和音频生成视频，不需要把“动作底片 + 独立改嘴”作为固定前提。它们从模型形态上接近实时生成路线，从使用方式上仍属于需要自己部署的模型，不是上述即买即用 API。

- FlashHead Lite 官方宣称单张 RTX 4090 支持实时；Pro 官方实时条件为两张 RTX 5090，需匹配加速配置。
- FlashTalk 官方的约 32 FPS、0.87 秒启动数据基于 **8×H800**，不能套用到普通单卡。

有 GPU 和工程资源、希望超出局部口型效果时，再考虑这一组。本轮未复现其性能。

### 为什么“嘴动了”仍可能不好看

应检查具体问题，而不是笼统判定开源模型效果都不好：嘴部纹理和牙齿细节、人脸裁剪抖动、下巴融合边缘、侧脸遮挡、底片原本张嘴、光照差异，都可能影响观感。MuseTalk/Wav2Lip 的结果尤其依赖人物素材与回贴设置。生成模型则还要检查身份变化、手部和跨片段连续性。[Wav2Lip 调参说明](https://github.com/Rudrabha/Wav2Lip)、[MuseTalk 说明](https://github.com/TMElyralab/MuseTalk)、[InfiniteTalk 已知限制](https://github.com/MeiGen-AI/InfiniteTalk)

**选型建议：**如果只希望角色不要僵硬，而口型模型带来的模糊和融合痕迹比不同步更明显，应把“漂亮的预制讲话动作”也纳入盲测，不必默认有口型推理就更好。

### GPU 成本怎么理解

以核查时 Runpod 定价页列出的 RTX 4090 **$0.74/小时**为例，假设一张卡恰好承载一条达标实时会话：100% 利用时裸算力约 $0.0123/有效分钟，10% 利用时约 $0.123；按每月 720 小时常驻则约 $532.80。这里只是利用率算术，**没有证明任一模型在该卡上满足实时或并发要求**，也不含存储、语音与维护。[Runpod GPU 定价](https://www.runpod.io/pricing)

租 GPU 不是唯一办法：离线动作生成可以短租或调用生成 API，生成完关闭算力；第三类动作编排正是把这部分成本前置并复用。

## 三、预生成动作编排：无口型推理，低成本增加动态表现

### 方案是什么

提前准备两组以上的人物短视频，运行时只切换播放状态：

```text
没有说话：播放待机动作（呼吸、眨眼、轻微头动）
正在倾听：播放倾听动作，或继续待机
正在思考：播放轻微思考动作，或继续待机
声音实际开始播放：切到讲话动作（自然张嘴、表情和适量手势）
声音结束 / 被打断：切回待机或倾听
```

讲话视频里的嘴会动，但嘴形不由当前这段语音计算；音频独立播放。它提供的是**发声状态一致**，不承诺逐字、逐音素一致。素材可以实拍，也可以用图生视频、LivePortrait 或其他离线生成方式制作一次后反复使用。

运行时无需专用 GPU 推理服务，也没有按会话分钟计算的口型生成费用；仍有视频解码、素材制作、存储与流量，以及对话/语音服务成本。因此应称“免实时口型推理”，不称“零成本、完全不使用任何 GPU”。

### 网上有没有类似方案

有，以下证据证明这是一条已有实践的产品方向；它们并不都是可以采购的真人视频 API。

| 参考 | 官方能确认的能力 | 与本方案的关系 |
| --- | --- | --- |
| [Kindroid Animated Avatars](https://kindroid.ai/v2/docs/selfies-video-selfies-avatars/) | 预生成头像动画，用于头像和语音通话；[FAQ](https://kindroid.ai/v2/docs/faqs/)描述一组 idle / talking 动画 | 最接近“预制待机与讲话动作”的产品先例；官方未披露播放器全部内部实现，不据此推断其底层成本 |
| [veadotube mini](https://veado.tube/docs/usage/mini/) | 音量触发开嘴/闭嘴状态，支持动画图片、眨眼和多个状态 | 证明轻量状态动画可以表达“正在说话”；偏 PNGTuber，不是写实人像推理 |
| [Live2D Cubism](https://docs.live2d.com/en/cubism-sdk-manual/lipsync/) | 可通过音量映射嘴部开合参数 | 风格化二维角色的低成本替代；仍需角色资产与图形渲染 |
| [LiveTalking 动作编排](https://doc.livetalking.ai/docs/usage/) | 支持自定义视频和静音动作播放 | 提供可借鉴的动作机制；标准讲话路径仍可调用口型模型，不能宣称默认已免模型 |

Kindroid 现在还另有 **Live Avatar Video** 实时口型功能，应与 Animated Avatars 分开理解，不能用实时视频价格或能力描述预制动画。[Kindroid 通话说明](https://kindroid.ai/v2/docs/voice-calls-and-video-calls/)

Kindroid 页面在本轮直接抓取时部分返回加载占位；上述动画描述来自官方页面的可检索内容。因此将其作为产品先例，不作为完整内部架构的验证证据。veadotube 官方还提供 [WebSocket 状态控制接口](https://veado.tube/docs/tech/api/nodes/)，可供状态驱动思路参考。

### 为什么值得作为低成本首选

在“没有专用 GPU、强调陪伴感与及时回应、可接受非精确口型”的前提下，这条路线有明确优势：

- **保留素材画质。** 在线不重新生成嘴部，避免低质量改嘴产生的模糊与拼接痕迹；前提是原素材本身合格。
- **人物有动作。** 待机能眨眼、呼吸，讲话能张嘴、点头；不必一直显示静态照片。
- **响应路径短。** 素材加载完成后即可切换，不等待视频模型生成；音频本身的生成延迟仍存在。
- **无需持续口型推理。** 同一组动作可以重复用；时长与并发仍增加语音、解码播放和网络成本。
- **可维护。** 不满意时直接更换动作素材，无需训练或调节口型模型。

以上是架构与产品判断，不能据此保证所有人物都比口型模型自然。主要代价是嘴形不匹配、动作重复和切换跳变。

### 适合与不适合的场景

| 更值得优先试 | 更应保留真实口型同步 |
| --- | --- |
| 网页助手、小尺寸头像、轻量陪伴聊天 | 大屏真人近景、长时间正脸口播 |
| 风格化角色、重视内容与响应速度 | 发音教学、读唇相关体验 |
| 高频使用、预算有限、无模型运维团队 | 对逐字同步与写实可信度有明确验收要求 |

不建议把“大部分人分不清音频和口型”写成事实：本轮没有找到支持该普遍比例的证据。已有研究讨论了人对**同一段语音的音画时间偏移**的容忍度及情境影响，但不能推出“任意讲话动作配任意语音不会被察觉”。应验证的是用户在目标界面里是否觉得自然、是否在意不同步，而不是假定用户看不出来。[Eg & Behne：实时对话中的音画时间整合](https://www.isca-archive.org/avsp_2013/eg13_avsp.html)

### 给 OpenRealtime 的建议新增方案

**建议产品名称：轻量动作模式。定位：无需实时口型推理，让人物在待机和讲话时自然活动。** 当前是待实现方案，不是已经上线的模式。

| 项目 | 建议 |
| --- | --- |
| 最小素材包 | 待机、讲话各一组；倾听/思考可以先复用待机 |
| 更自然的素材包 | 多段待机、多段讲话，加入少量点头、微笑等变化 |
| 动作要求 | 机位、人物大小、光照一致；讲话动作有自然开闭嘴；首尾容易衔接 |
| 切换依据 | 以音频实际开始/结束播放为准，不能收到文本就开始讲话 |
| 打断 | 音频停播后及时结束讲话状态，不等整段讲话视频播完 |
| 防机械重复 | 多素材轮换、可衔接边界、避免刚重复同一片段；不要为接完动作而延迟回答 |
| 异常回退 | 素材未准备好时展示待机或静态图，继续语音；不偷偷启动 GPU 口型服务 |
| 可选加强 | 根据音量/停顿控制开闭嘴或讲话状态；这仍不是音素级口型同步 |

建议先用同一人物、同一回答比较“静态图”“预制动作”“口型模型”三组，让用户评价自然度、重复感、回应及时性与整体满意度。如果预制动作达到需求，就不必为口型精度支付持续推理成本。

## LiveTalking、OpenTalking 与本项目处在什么位置

它们是把模型、资产和会话组合起来的工程框架，不能作为“某个口型模型”的同义词。

| 项目 | 与三类选型的关系 | 本轮核查结论 |
| --- | --- | --- |
| [LiveTalking](https://github.com/lipku/LiveTalking) | 主要承载多段式合成；典型视频模板属于“动作驱动 + 口型对齐”，另有动作编排机制 | 可作为模型与推流参考；有自定义动作不等于整个说话链路免口型推理 |
| [OpenTalking](https://github.com/datascale-ai/opentalking) | 典型 QuickTalk / 视频模板属于“动作驱动 + 口型对齐”；也覆盖图片、面部驱动及生成式模型 | 本地与远端推理分离；Mock 是链路验证，不是数字人效果；FlashHead 本地有 HTTP 和 WebSocket 两种客户端，实际实时性要按运行路径验证 |
| OpenRealtime | 当前有第一类托管接入，以及第二类动作底片 + 自有口型渲染链路 | 已有素材管理与循环预览；第三类独立的待机/讲话切换会话模式仍需新增 |

当前本地口型默认是 Wav2Lip 256 路径，而不是历史文档中的 96。已有 M1 16 GB/MPS 单会话记录约 28.67 FPS 推理合成吞吐、25 FPS 接收帧率；首块上传至服务端首音交付约 872–883 ms，不含 TTS 首包、前端攒块与浏览器扬声器延迟。它只说明特定配置曾跑通，不能推广成纯 CPU、多人物、多并发都达标。

**推荐对用户提供三个明确选项：**“实时数字人（API 付费）”“自部署合成（模型与算力）”“轻量动作（预制素材，无实时口型）”。在第三项正式实现前应标记为规划中，不能让用户误以为只要选一个动作就能跳过口型服务。

## 最终选型建议

1. **预算够、追求更完整的真人说话体验：**先试 Anam / LiveAvatar；使用自己的中文音频和角色做样例对比，再根据计费时长与并发选套餐。
2. **有 GPU、希望自部署：**先比较 MuseTalk 与当前口型基线；需要更多头动表情，再测 JoyVASA/LivePortrait、Ditto 或 FlashHead；离线模型优先用于素材制作。
3. **无专用 GPU、低成本、只要人物不僵硬：**优先验证预生成动作编排。这是本项目应补充的独立路线，不应强制用户经过口型模型。
4. **没有服务器 GPU，但仍要求嘴形跟随语音：**可额外评估 DH_live 等端侧轻量方案，或接受人物专训的 FeatherTalk；单独核对资产和授权条件。
