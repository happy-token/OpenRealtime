# 连续实时口型优化

本轮在上一次口型合成修复上继续优化，保持 `stride=2`、`blend=0.6`、768×768 输出和 256 模型输入。LiveTalking/OpenTalking 应用没有运行或修改，参考工作树的既有差异哈希保持不变。

## 按顺序实施的结果

1. **连续音频衔接**：前端不再等待整个 generation 完成才上传。大约收到 300 ms 可用音频就开始发送；同一 generation 的请求串行编号，后端保留连续 PCM、原始 STFT 时间网格和跨批预测。只在最终结束处补齐，不在 HTTP 分块处填静音。重采样保留全局相位，覆盖 16 kHz、24 kHz、44.1 kHz。上传顺序错误会显式拒绝。
2. **首批低延迟**：第一批为 2 帧，之后按可用音频增长至最多 8 帧。非最终分块起播时保留至少 480 ms 的音频，再安排 12 帧（480 ms）空闲前导，覆盖首批与下一批的计算；两条队列各容纳 16 帧，空闲生产按播放时钟推进。音频暂未到达时只在剩余播放余量内等待，避免人为插入停顿。保留真实模型音频前瞻，首音和结束状态由服务端音轨播放进度报告，替换原先“上传成功 + 700 ms + 音频长度”的估算。该状态是服务端向 WebRTC 发送端交付音频的进度，不是浏览器扬声器的精确硬件播放时刻。
3. **人脸编码缓存评估**：实验拆开人脸编码与解码，比较完整模型、GPU 特征缓存、CPU 特征缓存。每批 4 个预测，测得约 245.4 / 250.4 / 246.8 ms；每帧特征占 4,146,176 字节，251 帧约 0.97 GiB。该次实验没有显示收益，因此没有向生产加入这套缓存。实验脚本和结果保存在验收资产目录，不能把“不重复编码”直接等同于更快。
4. **遮罩与中间帧**：素材加载时跟踪原始嘴部纹理，以固定参考和往返一致性检查防止累计漂移；只平滑遮罩位置，不平滑预测口型。`stride=2` 的中间帧通过小区域双向光流对齐嘴部轮廓再混合，低置信度处回退到线性中间帧。只在最终合成时向原脸应用空间羽化。光流使用 64/96 像素宽的分析区域，跟踪中心量化到素材裁剪像素，以控制实时开销。

另外修复了旧 generation 的取消请求晚到时清空新回答的问题；已经入队的尾帧和前导取消后也会正确更新状态；没有更新回答在途时回收取消帧占用的播放时隙，保留已交付时间戳的递增约束。浏览器实机验收暴露并修复了原生 `fetch` 的 receiver 绑定问题，相关回归测试已补上。

## 完整视频与测量

交付：`research-assets/avatar-evaluation/2026-09-07/compositing-fix/openrealtime-streaming-final.mp4`。

播放：`http://localhost:3010/digital-human/evaluations/openrealtime-streaming-final-2026-09-07.mp4`。

该视频来自当前 8010 服务真实 WebRTC 接收端，包含原有 4.95 秒和 20 秒两段语音、完整人物画面和音轨，未剪切语句、未加速。对应采样为 `streaming-acceptance.json`。分块为 320 ms，每约 320 ms 到达一块（`--pace 1`），模拟音频按播放速度持续到达。

| 两段最终状态 | completed / completed |

高分辨率光流版本约 24.50 FPS，缩小分析区域后恢复实时吞吐。进一步的实时到达测试发现，4 帧队列无法容纳 8 帧计算批次，且音频短暂未到时立即补空闲帧会产生段间停顿；最终使用上述队列和有界等待策略。最早约 300 ms 开口的实验版本未达到该连续性要求，因此最终选择约 880 ms 的服务端起播延迟。这个数值不包括 TTS 首包生成、前端攒块或浏览器硬件播放延迟。

相比上一轮完整上传录制的 28.51 FPS，这次保持了相近吞吐；主要收益是连续分块输出、较早开始响应、段间稳定性和真实播放状态反馈。

完整视频已在播放器打开并复核张嘴、闭嘴和人物稳定性。源素材的嘴部动作较克制，不能据此承诺每个人物或逐音素的同步精度。当前吞吐仍只代表 M1 16 GB、MPS、单会话条件，多会话与更高分辨率不在本次验收范围。

中途取消后立即上传新回答的独立实录为 `streaming-interruption-final.mp4`，采样同名 JSON：旧回答 cancelled、新回答 completed；新回答首音交付约 482 ms，完整 124 帧，最大音频帧迟到约 3.8 ms，无缺音空闲帧。该测试的新回答一次性上传，不能与上表的实时分块起播延迟直接比较。
