# 响应完成前沿与 TTS 清理归属

日期：2026-10-07。前置提交 `0d5cee4`；对应 ADR0137、实施计划阶段3。本批补 Core 响应完成边界和真实 TTS 关闭确认，不关闭阶段3/G3。

## 修复行为

最后一段模型文本不代表它的已听历史依据可以一直沿用。模型 Completed、等待 TTS、空音频/委派结算以及公开 ResponseCompleted 之前，都再次核对当前输入、关联和模型可见历史投影。只有样本位置移动、已听文本未变时继续成功；实际可见历史改变时撤权并明确失败，要求新的公开回复版本。

TTS 收到音频、字幕或生成终态时也重验这一依据。若 TTS 子任务先发现过期，正在等待下一段模型输出的父任务立即获知错误，不能直到模型总超时才处理。过期上下文作为协议失败，不误计为普通 TTS 供应商请求失败。

## 满队列与取消所有权

失败输出泵已经退出时，TTS 默认64项事件队列可能填满。直接发送 Cancel 而无人消费，会连取消回执一起堵住。本批复用既有能力会话，私有消费匹配 speech 的关闭终态，同时取消供应商，不向用户重放排队音频。

所有模型回复的失败、总超时和用户取消，以及直接语音投递的失败/取消都加入同一个每回复关闭任务；等待者 shield 原任务，重复调用不另建清理。关闭任务启动前同步锁住 TTS 准入，只有匹配终态和真实取消确认都成功才解锁。取消等待者本身退出不表示供应商关闭。超时或实际关闭错误保留原失败原因和清理诊断，并阻止模型请求、外部 StartSpeech 及语音/模型结果投递使用尚未确认的 TTS 会话。异步准备完成、发送 StartTts 之前也检查锁。

Native TTS 的双工和提交后合成都显式拥有实际 provider 迭代器；即使输出背压使流停在 yield，也必须进入该迭代器的 finally。关闭错误用内部 TtsFailed.cleanup_failed 区别于普通业务错误，不发布成功 Cancelled 确认；后续 Start 拒绝复用故障会话。重复取消不再取消正在执行的 finally。Native close也由一个共享任务持有，所有关闭等待者加入同一个任务；先解除事件队列背压，然后等待实际provider/预热/残留任务结束，再关闭transport，具体关闭错误持续反馈。取消关闭等待者不会二次取消finally，也不会伪造成功关闭。外部播报同样把关闭故障和取消超时同步给Core准入锁。

正常一般补充仍保留 actor 签发的当前句许可。清理未确认时新用户输入仍进入 Journal；下一轮给明确失败，不继续请求模型或播放混合音频。原清理暂停回归据此修正契约，没有用延长等待掩盖问题。
