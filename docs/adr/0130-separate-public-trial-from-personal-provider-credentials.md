# Separate public trial from personal provider credentials

OpenRealtime will offer an unauthenticated Public Trial of a published Avatar's complete realtime conversation, funded by Platform Provider Credentials configured by the operator in server-side `.env`. Avatar creation and video generation require an authenticated user and that user's own provider credentials. For each paid realtime capability, the system visibly uses the authenticated user's Personal Provider Credential when saved; otherwise it uses the corresponding Platform Provider Credential, including after the user deliberately clears their key. There is no separate source toggle. A configured personal key that is invalid or exhausted only produces a visible failure and never silently switches to the platform key. Personal credentials are saved to the user's account until removed and are used only for that user's requested operations, never for another visitor's trial. This boundary trades a simpler automatic fallback for predictable cost ownership and an accurate privacy promise.

Platform Speech Admission rejects a full-capacity attempt immediately with a visible busy state and manual retry. It governs use of the operator's ASR or TTS capacity; the operator's LLM key alone does not consume this speech slot. An unauthenticated Public Trial always lasts at most three minutes by default. An authenticated conversation has the same limit when it uses platform ASR or TTS, but not when both speech services use personal keys and only its LLM uses the platform key. The duration is deployment-configurable, and the browser is never the authority for capacity or spending permission.

The first public release gives platform ASR and platform TTS separate, configurable concurrency limits of one each by default. A conversation using only platform ASR and another using only platform TTS may run at the same time. A conversation using both must obtain both slots before starting. The product sets neither a per-visitor daily attempt count nor a site-wide daily trial budget; provider quota exhaustion still makes the affected platform capability unavailable. These limits are explicit operator choices rather than assumptions that one short session bounds total spend.

The shared provider accounts used for public trials must stop at exhausted quota or have hard spending limits because the product imposes no daily total budget. HappyImage image generation follows the authenticated user's HappyImage account quota, as established in ADR-0094 and ADR-0105; the current server-side `HAPPYIMAGE_API_KEY` path must not become a public shared-paid generation route. Until per-user quota attribution is working, that paid action remains unavailable to ordinary website users.

After a Personal Provider Credential is saved, the account settings display only its configured state and a short masked suffix. Users can replace or delete it, but cannot retrieve its full plaintext through the product UI or API.

Only authenticated users may submit Personal Provider Credentials. Unauthenticated visitors use the bounded Public Trial and cannot supply an anonymous temporary key. The application should use its previously chosen Casdoor user identity boundary rather than treating the existing administrator session as an ordinary user account.

The public release must support per-conversation credential selection across Avatar rendering, speech recognition, dialogue, and speech synthesis; server-startup-only environment selection is insufficient. A missing personal key may deliberately use the operator's key for realtime conversation, while a paid Avatar creation or video generation request cannot use that operator-funded fallback.

Ordinary website users may access a paid provider operation only after its personal credential or per-user account quota, ownership check, and permission path have been verified end to end. Existing Vidu, LTX, LiveAvatar, and similar server-environment-funded operations stay closed to ordinary users until each path satisfies that rule; availability of an operator key never grants a paid-creation entitlement.

Quota status is checked before a paid operation only when the provider supplies a reliable read-only balance or entitlement endpoint. The UI never invents a remaining balance. A quota failure during an operation identifies whether the affected allowance belongs to the platform or the signed-in user, preserves the chosen credential source, and offers an appropriate next action.

If ASR or TTS quota is exhausted during a voice conversation, the current voice session ends with a clear reason and its existing conversation record remains available. After replacing a personal key or waiting for platform quota to recover, the user starts a new voice session. The product does not silently switch credentials, browser speech, or interaction mode to keep a failed voice session alive.
