# StatusInquiryClassifier plugin, and single-in-flight delegation per session

**Amended by ADR-0045:** the StatusInquiryClassifier and pull-based progress model remain accepted, but the single-in-flight delegation constraint is superseded. The Work Registry may now track multiple concurrent Delegated Tasks across named Agents.

ADR-0006 presupposes the system can tell a progress check ("怎么样了?") apart from a genuinely new topic once a delegation is pending, but never specifies how. This project's established answer to that class of ambiguity is a swappable classifier Protocol with a documented-as-minimal shipped default, not a bespoke design — `StatusInquiryClassifier.is_status_inquiry(*, text, generation)` is that plugin, with `KeywordStatusInquiryClassifier` (a small builtin phrase set: "怎么样了"/"好了吗"/"how's it going"/"any update"/etc.) as the default, same shape as `AddresseeClassifier` and `DualIntentClassifier`. We rejected hardcoding "any turn during a pending delegation is always a status check" — that would make a slow or stuck delegation impossible to abandon by voice, since every follow-up would be swallowed as a progress query instead of ever reaching the Router again. We also rejected the opposite hardcode, "always treat it as a new topic" — that defeats the entire point of ADR-0006's pull-based status model, since the user would never be able to ask "how's it going" without cancelling the very delegation they're asking about.

We also decided only one delegation may be in flight per session in v1 — no queuing, no parallel dispatches. A `UserTextFrame` arriving while `ConversationKernel` already has a pending session is always resolved as exactly one of the two cases above: answered from the cached update under the existing lease (no re-dispatch), or an implicit supersession that cancels the pending session/task and then proceeds as an ordinary new turn. We considered allowing a second concurrent delegation (e.g. the user starts a new task before the first resolves) but rejected it for v1: it would require deciding how two independent delegated results interleave with each other and with the single-Ack model from ADR-0006, and the PRD's own priority is getting one generalized delegation path working end-to-end, not concurrent multi-delegation scheduling. Cancellation-by-supersession here is a promptness optimization, not the correctness mechanism — the Generation-lease check already in `_await_delegation` (ADR-0001) is what actually prevents a stale result from being spoken even if cancellation is skipped or races (e.g. a VAD-driven `USER_SPEECH_ONSET` advances the generation without ever going through the text-supersession path).
